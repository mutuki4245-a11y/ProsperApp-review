# ProsperApp システム仕様書

作成日: 2026-07-03
対象: ProsperApp 店舗用アプリ
用途: 開発引継ぎ

## 1. 文書の位置づけ

本書は ProsperApp のシステム構成、画面、主要コンポーネント、外部連携、RPC/SQL運用を整理する。業務要件は `Docs/要件定義書.md`、SQL定義とRPCの俯瞰は `Docs/SQL_RPC概要.md`、作業時の最新方針は `HANDOFF.md` を参照する。

状態区分は以下の通り。

| 状態 | 意味 |
| --- | --- |
| 実装済み | 現行コード、DB、または運用設定に実装が確認できる仕様 |
| 一部実装 | アプリ側の処理はあるが、外部側の正式仕様、画面、または運用定義が残っている仕様 |
| 運用方針 | 実装タスクではなく、現行運用や開発時に維持する前提 |
| 後続仕様 | 未実装で、別途仕様定義してから実装する仕様 |
| 検討候補 | 効果や破棄契機を確認したうえで実装判断する改善案 |

## 4. 認証・認可

| 項目 | 状態 | 仕様 |
| --- | --- | --- |
| 認証方式 | 実装済み | Cookie認証を既定schemeとし、Google OAuth設定がある場合はGoogleをchallenge schemeにする。 |
| Google設定不足 | 実装済み | `GoogleDrive:ClientId` または `GoogleDrive:ClientSecret` が不足する場合、Google challengeを開始しない。 |
| 許可判定 | 実装済み | `GoogleAuthOptions.IsAllowed` が `AllowedEmails` と `AllowedDomains` を照合する。 |
| Cookie検証 | 実装済み | Cookie principal検証時にGoogle設定または許可条件を満たさない場合、principalをrejectしてSessionをclearする。 |
| Google token | 実装済み | Google access tokenは認証ticket作成時にSessionの `GoogleDriveAccessToken` へ保存する。 |
| 認可 | 実装済み | `MapRazorPages().RequireAuthorization()` によりRazor Pageを原則認証必須にする。`/Login` はPageModelの `[AllowAnonymous]` で認証前アクセスを許可する。 |
| logout | 実装済み | `/logout` はSessionをclearし、Cookie認証をsign outする。returnUrlはローカルURLのみ許可する。 |

### 6.1 画面UI仕様

| 領域 | 状態 | 仕様 |
| --- | --- | --- |
| 勤怠キャスト追加 | 実装済み | `/Closing/Attendance` のキャスト追加モーダルは、有効キャストをチェックボックス一覧で表示し、複数名を一括で出勤登録できる。既に当日勤怠があるキャストは重複登録しない。 |
| 勤怠時刻選択 | 実装済み | 勤怠入力の出勤時刻は19:00、退勤時刻は24:00をUI初期値にする。時刻選択肢はそれぞれの初期値を中心に前後12時間を表示し、刻みは `AttendanceMinuteStep` に従う。24:00以降の時刻はアプリ内では25:00、26:00のように表記する。 |
| 指名追加 | 実装済み | `/Slips/Edit` の指名追加では、指名種別のデフォルトを本指名にする。同伴は「19:29まで」「19:59まで」「20:59まで」「21:00以降」の4種類として扱う。 |
| 指名価格 | 実装済み | 指名追加UIでは指名種別の次に指名価格の選択UIを置き、1000円から20000円まで1000円刻みで毎回選択できる。指名価格は会計額に加算する。指名種別に応じたキャストバック計算は後続仕様として残す。 |
| 指名候補キャスト | 実装済み | 指名追加のキャスト候補は、退勤済みかどうかに関わらず、当日出勤キャスト全員を表示する。 |
| 自由入力明細 | 実装済み | 伝票には通常の商品明細とは別枠で、名前と価格を自由入力できる調整明細を追加できる。商品マスタには登録せず、価格は負値を許容し、当面は税区分や商品売上分類に分解せず会計合計額へ直接加減する。伝票/会計では通常商品とは別の明細グループとして表示する。 |
| `/Orders` 複数卓キュー | 実装済み | `/Orders` の注文キューは行ごとに対象卓または対象伝票を保持し、違う卓のオーダーも同じキューに入れて一括登録できる。登録時は注文行ごとの `slip_id` を含めて `add_store_order_lines` を呼ぶ。 |
| バックキャスト候補 | 実装済み | バック対象商品のバックキャスト選択候補は、先頭に「なし」を表示する。「なし」を選んだ注文行にはバックの摘要を付与しない。候補キャストは退勤済みかどうかに関わらず、当日出勤キャスト全員を表示する。 |
| 営業中会計額 | 実装済み | 営業中画面では卓ごとの会計額を常に隠し、画面右下寄りに固定表示する専用オーバーレイボタンに触れている間だけ会計額が見えるようにする。触れていない状態では会計額を静的テキストとして表示しない。 |
| カラオケ簡易入力 | 実装済み | 営業中画面と伝票詳細ではカラオケを商品マスタ上のシステム商品として扱い、伝票行またはオーダー行の `+` / `-` ボタンで数量を増減できる。営業中画面では数量変更を即時表示し、手動保存ボタンを置かず、短時間のデバウンス後に差分だけ自動保存する。伝票詳細へ遷移する前にも未保存分の保存を短く試みる。カラオケは1回200円固定で通常の商品小計に含め、サービス料20%の対象にする。同一伝票ではカラオケ注文行を1行に集約し、時刻列は入店時刻に固定する。 |
| 会計時領収書印刷 | 一部実装 | 会計確定時にSII製レシートプリンター向けの領収書印刷要求データを作成し、`ReceiptPrinter:BridgeUrl` の端末側ブリッジURLへHTTP POSTする。任意の `ReceiptPrinter:ApiKey` は `X-Receipt-Printer-Key` ヘッダーで送る。印刷失敗、タイムアウト、設定不足でも会計確定は完了扱いとする。領収書レイアウト、印字項目、再印刷画面、正式APIは後続仕様で定義する。 |

### 6.1.1 現場端末運用前提

現場運用は、営業中画面を操作する端末1台と、注文入力専用の `/Orders` 端末複数台で行う。

| 端末種別 | 画面モード | 主な役割 | 同期方針 |
| --- | --- | --- | --- |
| 営業中端末 | `sales-management` | 伝票作成、当日伝票一覧、カラオケ簡易入力、会計導線、締め導線を扱う。 | カラオケ数量や会計額は操作直後にローカル表示へ即時反映し、保存通信だけをデバウンスする。注文端末から登録された注文はDB保存後の再取得または画面更新で反映する。 |
| 注文端末 | `order-entry` | `/Orders` でopen伝票を選び、注文キューを作って一括登録する。複数台で同時利用できる。 | 注文キューと未送信ドラフトは端末ごとのlocalStorageに保持する。登録成功後のDB/RPC結果を共有状態とし、他端末のローカルドラフトとは同期しない。 |

### 6.2 現場操作性・レスポンス改善の実装状況

現場投入で効果が大きいものは実装済みとする。未実装の追加改善は、後続の検討候補として 6.3 と 14 に分けて扱う。

| 優先 | 状態 | 実装内容 |
| --- | --- | --- |
| 1 | 実装済み | 注文登録、勤怠保存、会計確定、自由入力明細保存、伝票詳細のカラオケ数量保存では、押下直後に送信ボタンを無効化し、処理中表示を出し、完了または失敗で必ず復帰する。営業中カラオケは保存ボタンを置かず、裏側のAjax保存で同じ復旧方針を満たす。失敗時は入力値とキューを消さず、同じ内容を再送できる。 |
| 2 | 実装済み | `/Orders`、営業中カラオケ、自由入力明細は「画面内ドラフト」を正式な操作単位にする。追加、数量変更、削除は即座に画面へ反映し、未送信ドラフトを `departmentId`、`businessDayId`、`slipId`、画面種別を含むキーで `localStorage` に保存する。ドラフトは端末内の復旧用状態であり、営業中端末と注文端末間で直接同期しない。登録成功時だけ該当ドラフトを削除する。 |
| 3 | 実装済み | 登録はドラフトをまとめて1回のPOST/RPCで送る。注文は既存の複数卓キューを維持し、カラオケは商品注文行の数量を伝票単位で一括保存し、自由入力明細も複数行を一括保存するRPCを用意する。営業中カラオケは最後の操作から短時間後に差分だけ自動保存し、1タップごとに保存RPCを呼ぶ実装にはしない。 |
| 4 | 実装済み | 候補データは画面初期表示でまとめて渡す。ただし営業中トップの指名候補は初期表示をブロックしないため、伝票追加モーダル表示時にGET handlerで遅延取得する。卓、商品、営業日状態はRazor表示時に取得し、操作中の数量変更では追加RPCを呼ばない。営業中トップは一覧に必要な列だけを取得し、詳細内訳は伝票詳細で取得する。 |
| 5 | 実装済み | マスタ系候補はサーバー側 `IMemoryCache` に初回成功時だけ保持する。対象は店舗一覧、店舗コンテキスト、卓、キャストマスタ候補、商品候補、商品管理カタログ、キャスト管理一覧とする。RPC失敗や環境変数未設定の結果はキャッシュしない。商品/カテゴリ保存、商品削除、商品並び順保存、キャスト登録/削除が成功した場合だけ該当店舗の関連キャッシュを破棄する。当日出勤キャスト候補の `get_order_attending_casts` は現行実装ではキャッシュしていない。 |
| 6 | 実装済み | 画面初期表示では既存RPCを保ち、依存しない取得をPageModel内で `Task.WhenAll` により並列化する。新しい集約RPCは作らず、`/`、`/Orders`、`/Slips/Edit`、`/Closing` の待ち時間を短縮する。 |
| 7 | 実装済み | 営業中トップでは締め作業専用の酒代、締め勤怠、未処理領収書、キャスト売上額調整状態を初期取得しない。締め可否判定に必要なデータは `/Closing` 表示時に取得する。 |
| 8 | 実装済み | 現在営業日の取得は店舗別に営業日締め成功までキャッシュする。営業日開始時は取得結果で更新し、営業日締め成功時は破棄する。RPC失敗、設定未完了、営業日なしの結果はキャッシュしない。複数インスタンス運用ではプロセス単位のキャッシュになるため、他プロセスで締めた営業日は次回プロセス再起動または明示破棄まで残り得る。 |
| 9 | 実装済み | 一覧RPCは対象営業日・対象伝票を先に絞ってから客、指名、注文、自由入力明細を集計する。`get_business_day_slips` と `get_cast_sales_adjustment_slips` は全期間集計して最後に絞る形にしない。 |

### 6.3 画面/処理別RPC呼び出しとキャッシュ方針

画面遷移や保存処理で実行するRPCは以下を標準とする。マスタ系と現在営業日はアプリサーバーの `IMemoryCache` を使い、伝票、会計、締め可否など営業中に変わる値は原則として最新取得する。

| 画面/処理 | 実行するRPC | キャッシュ方針 |
| --- | --- | --- |
| `/` 初期表示 | `get_store_context`, `get_current_business_day`, `get_store_tables`, 営業日がある場合は `get_business_day_slips` | 店舗コンテキスト、現在営業日、卓はキャッシュ対象。伝票一覧は会計額、客数、指名、注文、カラオケが変わるため動的取得。 |
| `/` 伝票作成モーダルの指名候補 | `get_current_business_day`, `get_order_attending_casts` | 現在営業日はキャッシュ対象。出勤キャスト候補は現行実装では都度取得する。キャッシュ化する場合は、勤怠保存、営業日開始、営業日締めで営業日単位キャッシュを破棄する。 |
| `/` 伝票作成POST | 画面再表示用ロードとして `get_store_context`, `get_current_business_day`, `get_store_tables`, `get_business_day_slips`, 指名ありの場合は `get_order_attending_casts`。保存で `create_store_slip` | マスタと現在営業日はキャッシュ対象。出勤キャスト候補は現行実装では都度取得する。`get_business_day_slips` は入力検証そのものではなく、POST失敗時や保存後の営業中画面再描画に使う。 |
| `/` カラオケ自動保存 | `save_store_karaoke_lines` のみ | `businessDayId`, `slipId`, `quantity` を画面状態から送信し、対象営業日・対象店舗・open伝票・数量の検証とカラオケ商品行への集約は保存RPC側で行う。店舗コンテキスト、卓、伝票一覧の再取得は不要。 |
