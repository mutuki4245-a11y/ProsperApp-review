# ProsperApp システム仕様書

作成日: 2026-07-03
対象: ProsperApp 店舗用アプリ
用途: 開発引継ぎ

## 1. 文書の位置づけ

本書は ProsperApp のシステム構成、画面、主要コンポーネント、外部連携、RPC/SQL運用を整理する。業務要件は `Docs/要件定義書.md`、SQL定義とRPCの俯瞰は `Docs/SQL_RPC概要.md`、作業時の最新方針は `HANDOFF.md` を参照する。

会計フロー第1段階は、営業中トップ `/`、Repository、SQL、SII印刷JavaScript、`prosper-rpc` allowlistのソースとして実装済みである。リモートDBへのSQL適用とEdge Functionデプロイは未実施である。したがって、本書ではこの変更単位を「ソース実装済み（未適用）」と表記し、既存リモート環境の稼働状況とは区別する。

状態区分は以下の通り。

| 状態 | 意味 |
| --- | --- |
| 実装済み | 現行コード、DB、または運用設定に実装が確認できる仕様 |
| ソース実装済み（未適用） | アプリ・SQL・Edge Functionのソースには実装済みだが、リモートDBまたはEdge Functionへ未適用の仕様 |
| 置換済み | 旧実装を削除し、記載した新しい導線または契約へ置き換えた仕様 |
| 参照注意 | 旧スナップショットであり、本文に記す現在の一次ソースと併読が必要な資料 |
| 一部実装 | アプリ側の処理はあるが、外部側の正式仕様、画面、または運用定義が残っている仕様 |
| 運用方針 | 実装タスクではなく、現行運用や開発時に維持する前提 |
| 後続仕様 | 未実装で、別途仕様定義してから実装する仕様 |
| 検討候補 | 効果や破棄契機を確認したうえで実装判断する改善案 |

## 4. 認証・認可

| 項目 | 状態 | 仕様 |
| --- | --- | --- |
| 認証方式 | 実装済み | Cookie認証を既定schemeとし、Google OAuth設定がある場合はGoogleをchallenge schemeにする。 |
| Google設定不足 | 実装済み | `GoogleDrive:ClientId` または `GoogleDrive:ClientSecret` が不足する場合、Google challengeを開始しない。 |
| 許可判定 | 実装済み | `GoogleAuthOptions.IsAllowed` が `AllowedEmails` と `AllowedDomains` を照合する。 |
| Cookie検証 | 実装済み | Cookie principal検証時にGoogle設定または許可条件を満たさない場合、principalをrejectしてSessionをclearする。 |
| Google token | 実装済み | Google access tokenは認証ticket作成時にSessionの `GoogleDriveAccessToken` へ保存する。 |
| 認可 | 実装済み | `MapRazorPages().RequireAuthorization()` によりRazor Pageを原則認証必須にする。`/Login` はPageModelの `[AllowAnonymous]` で認証前アクセスを許可する。 |
| logout | 実装済み | `/logout` はSessionをclearし、Cookie認証をsign outする。returnUrlはローカルURLのみ許可する。 |

### 6.1 画面UI仕様

#### 会計フロー第1段階の実装済み範囲

下表の「会計伝票と会計準備中」「顧客名の確定」「会計伝票のヘッダと客情報」「会計伝票の税額」「会計伝票再印刷」「会計伝票印刷モデル」「会計伝票の物理印刷」「0円会計」「決済方法入力」は、いずれも**ソース実装済み（未適用）**である。会計導線は `/` の会計モーダルにあり、`/Slips/Edit` には会計用のhandler、partial、JavaScriptを置かない。

会計伝票RPCは `print_data` に加えて、会計確認画面だけに使う `review_data` を返す。`print_data` 自体には顧客名、バック対象キャスト、注文時刻、識別子を含めない。`review_data` は紙面用データではない。

| 領域 | 状態 | 仕様 |
| --- | --- | --- |
| 勤怠キャスト追加 | 実装済み | `/Closing/Attendance` のキャスト追加モーダルは、有効キャストをチェックボックス一覧で表示し、複数名を一括で出勤登録できる。既に当日勤怠があるキャストは重複登録しない。 |
| 勤怠時刻選択 | 実装済み | 勤怠入力の出勤時刻は19:00、退勤時刻は24:00をUI初期値にする。時刻選択肢はそれぞれの初期値を中心に前後12時間を表示し、刻みは店舗別マスターの `attendance_minute_step` に従う。24:00以降の時刻はアプリ内では25:00、26:00のように表記する。 |
| 指名追加 | 実装済み | `/Slips/Edit` の指名追加では、当日出勤キャストをコンボボックスから選択し、店舗別DBマスタの有効な指名種別を選択する。初期定義は本指名、場内指名、同伴「19:29まで」「19:59まで」「20:59まで」「21:00以降」の6種類とする。 |
| 指名料金 | 実装済み | 指名追加UIでは指名種別の次に指名料金の選択UIを置き、1000円から20000円まで1000円刻みで毎回選択できる。指名料金は `item_type = 'nomination_fee'` のシステム商品として注文行へ自動追加し、会計額に加算する。指名登録時は店舗別の指名バック設定を参照し、有効かつ0円より大きいバック単価をキャスト別の営業実績として保存する。 |
| 指名バック設定 | 実装済み | `/Management/NominationBacks` で店舗別DBマスタの指名種別ごとにバック単価と有効/無効を保存する。商品バックとは別枠のマスタであり、指名登録時に営業実績へスナップショット保存する。 |
| 料金・バック用語 | 運用方針 | 会計額へ加算する料金は指名料金、指名時にキャストへ支払うバックは指名バック、商品注文時にキャストへ支払う通常バックはドリンクバック、商品注文バック対象が当該伝票の指名キャストだった場合のバックは担当バックと呼び分ける。 |
| 設定デバッグ削除 | 実装済み | `/Settings` の管理者解除後に「マスタ以外のテーブルのレコードを削除する」ボタンを表示する。実行時は確認ダイアログとサーバー側解除トークンを要求し、`store.delete_non_master_records` で選択店舗の営業日、出勤、伝票、注文、会計、バック集計を削除する。マスタ表は削除しない。 |
| 指名候補キャスト | 実装済み | 指名追加のキャスト候補は、退勤済みかどうかに関わらず、当日出勤キャスト全員を表示する。 |
| 自由入力明細 | 実装済み | 伝票には通常の商品明細とは別枠で、名前と価格を自由入力できる調整明細を専用モーダルから1件ずつ追加できる。商品マスタには登録せず、価格は負値を許容し、当面は税区分や商品売上分類に分解せず会計合計額へ直接加減する。伝票/会計では通常商品とは別の明細グループとして表示する。会計伝票では通常オーダーとは別枠で、摘要と符号付き金額だけを個別行印字する。未保存入力は会計時ではなくモーダルを閉じる時点で確認し、保存せず閉じる場合は破棄する。 |
| `/Orders` 画面構成 | 実装済み | `/Orders` は注文端末専用の独立画面として、上部タブ、業務フローナビ、フッター、マスタ設定、営業中への戻り導線を表示しない。管理者設定は画面右上のボタンとして残す。卓番選択、商品一覧、注文キューを3パネル横並びにし、画面全体は縦横ともスクロールさせず、各パネル本文だけを縦スクロールにする。卓番選択では入店時刻ではなく客名を表示し、客名が取れない場合は人数を表示する。 |
| `/Orders` 複数卓キュー | 実装済み | `/Orders` の注文キューは行ごとに対象卓または対象伝票を保持し、違う卓のオーダーも同じキューに入れて一括登録できる。画面上は卓番ごとにグルーピングし、件数と小計を表示する。登録時は注文行ごとの `slip_id` を含めて `store.add_order_lines` を呼ぶ。 |
| バックキャスト候補 | 実装済み | バック対象商品のバックキャスト選択候補は、先頭に「なし」を表示する。「なし」を選んだ注文行にはバックの摘要を付与しない。候補キャストは退勤済みかどうかに関わらず、当日出勤キャスト全員を表示する。 |
| 営業中会計額 | 実装済み | 営業中画面では卓ごとの会計額を常に隠し、画面右下寄りに固定表示する専用オーバーレイボタンに触れている間だけ会計額が見えるようにする。触れていない状態では会計額を静的テキストとして表示しない。 |
| カラオケ簡易入力 | 実装済み | 営業中画面ではカラオケを伝票行の `+` / `-` ボタンで増減できる。数量変更を即時表示し、手動保存ボタンや短周期の自動保存は置かず、アプリ内遷移や他フォーム送信の前に未保存分を保存する。保存成功後だけ遷移または送信を続行し、保存失敗時は操作を止める。伝票詳細ではカラオケを指名料金と同じ自動システム商品として表示し、数量変更や保存操作は置かない。カラオケは1回200円固定で通常の商品小計に含め、サービス料20%の対象にする。同一伝票ではカラオケ注文行を1行に集約し、時刻列は入店時刻に固定する。 |
| 営業中一覧ハブ | 実装済み | 営業中トップの卓行をその場で展開し、客、指名、注文合計、注文件数、自由入力明細合計、会計伝票出力を確認できる。営業中トップには見込み売上として、取消以外の伝票の会計額合計を参考表示する。会計額はその時点で計算できる税込・サービス料込みの最終請求額とし、営業中の参考値なので大きく目立たせない。見込み売上は営業中一覧ハブと同じ10秒ポーリング/フォーカス復帰で更新する。`open` の展開行には客・指名・自由入力明細の対象別編集を置き、単一モーダルが `/Slips/Edit` の対象別部分表示を動的取得して、既存の保存・検証を実行する。保存成功後は一覧を再取得し、非`open`・取得不能時は編集不可表示にする。注文訂正、数量変更、注文取消は `/Slips/Edit` に残す。カラオケ下書きがあるときは対象別編集のPOST前に保存成功を必須とする。注文明細は同じ商品かつ同じバック対象キャストでまとめ、注文時刻一覧や細かい内訳は必要時にアコーディオンまたはモーダルで開く。注文時刻一覧は会計伝票には印字しない。 |
| 会計伝票と会計準備中 | ソース実装済み（未適用） | 営業中トップの `store.issue_checkout_statement` が退店時刻、未退店客、`checkout_ready` を固定し、紙面用 `print_data` と会計確認用 `review_data` を返す。会計伝票は支払前の確認用で、自由入力明細と金額サマリーを出すが、支払方法、預り金、釣銭、識別子、バック情報を出さない。物理印刷状態はlocalStorageで管理し、未完了では会計確定できない。再印刷は端末保存値を使い、欠落時だけ読み取り専用RPCで復旧する。 |
| 顧客名の確定 | ソース実装済み（未適用） | 顧客名は注文端末と締め時のキャスト売上額調整一覧で使う伝票内の内部識別であり、領収書宛名には使わない。`open` の伝票だけで変更でき、`checkout_ready` と `checked_out` では画面・RPCの両方で変更を拒否する。訂正は会計準備解除または会計取消後に行う。 |
| 会計伝票のヘッダと客情報 | ソース実装済み（未適用） | `checkout-statement-v1` には店舗表示名、卓番、入店時刻、退店時刻、客数を出力する。顧客名、指名・バック情報、`checkout_id`、`slip_id`、`slip_no` は紙面に含めない。 |
| 会計伝票の税額 | ソース実装済み（未適用） | 金額サマリーは小計、サービス料、内消費税（10%）、合計の順に出力する。内消費税は `round(total_amount * 10 / 110)` の参考表示であり、会計額へ加算しない。 |
| 会計伝票再印刷 | ソース実装済み（未適用） | `checkout_ready` の間は自由に再印刷でき、紙面に再印刷表記や印刷履歴を持たせない。同一端末では保存済み `print_data` を使い、ローカルデータがない場合だけ `store.get_checkout_statement_print_data` で復旧する。 |
| 会計伝票印刷モデル | ソース実装済み（未適用） | 会計伝票は `checkout-statement-v1`、領収書は `checkout-receipt-v2` の別 `print_data` とする。旧 `ReceiptPrintRequest` は削除済みで、会計伝票は支払方法、預り金、釣銭、領収書宛名を持たない。 |
| 会計伝票の物理印刷 | ソース実装済み（未適用） | SII Web SDK Serverへの接続層は領収書と共用し、会計伝票のレイアウトは `sii-checkout-statement-printer.js`、領収書のレイアウトは `sii-receipt-layout.js` に分離する。 |
| 0円会計 | ソース実装済み（未適用） | 会計額が0円の場合は、決済方法なしで会計確定できる。会計画面では支払方法選択、預り金、釣銭入力を必須にせず、「請求なし 0円」と表示する。領収書や会計結果でも同じ表示を使い、現金0円やカード0円の支払明細は作成しない。 |
| 決済方法入力 | ソース実装済み（未適用） | 0円以外は現金、CAT、PAYPAYの支払行を入力し、初回追加時だけ残額を初期値にする。残額、超過額、支払合計を表示し、確定時に合計不一致なら送信しない。現金では預り金と釣銭を入力・表示する。 |
| 誤卓防止表示 | 実装済み | 伝票詳細と会計モーダルでは、卓番、客名またはラベル、人数、利用時間、合計を同じ位置関係で確認できるようにする。注文追加や会計操作中に対象伝票を見失わないことを優先し、伝票詳細自体を画面共有キューの置き場所として扱わない。 |
| 会計確定前確認 | 実装済み | 会計モーダルでは追加ページを増やさず、確定ボタン周辺に卓番、客数、退店時刻、合計、支払内訳、現金預かり、釣銭を常時表示する。会計確定直前の確認は同じモーダル内で完結させる。 |
| 会計時領収書印刷 | ソース実装済み（未適用） | 会計確定の成功応答を受けた時だけ、SII製レシートプリンター向けの最初の領収書印刷要求データを作成する。同じブラウザが `siiWebSdk.js` の `PrinterManager` 経由で端末ローカルのSII Web SDK Serverへ接続して印刷する。80mm紙には発行者情報、宛名、会計確定の実日付、「ご飲食代として」、会計額、支払方法、内消費税額、税込み55,000円以上の収入印紙欄、担当者印欄を出し、識別子は出さない。発行者情報は会計確定時のスナップショットを使う。`checked_out` の手動再発行は営業中トップから行い、同じ端末に初回成功記録がある明示再出力だけ `再試行` を印字する。宛名は任意入力で保存せず、DBに印刷状態、印刷ジョブ、印刷履歴を持たせない。 |

> 発行者情報については、上表に残る `ReceiptPrinter` 設定を値の元とする暫定記載を廃止する。法人名・適格請求書登録番号は `company_master`、店舗表示名・住所・電話番号・ロゴは `department_master` を正とし、画面実装前のサンプル値も同マスタへseedする。`ReceiptPrinter` はプリンター接続設定だけを持つ。

> 同じく上表に残る `伝票番号` の印字は後続仕様では廃止する。`checkout_id`、`slip_id`、`slip_no` は端末内の対象特定とRPC契約にだけ使う内部識別子であり、領収書・会計伝票の紙面および顧客向け表示項目には含めない。

### 6.1.1 現場端末運用前提

現場運用は、営業中画面を操作する端末1台と、注文入力専用の `/Orders` 端末複数台で行う。

| 端末種別 | 画面モード | 主な役割 | 同期方針 |
| --- | --- | --- | --- |
| 営業中端末 | `sales-management` | 伝票作成、当日伝票一覧、カラオケ簡易入力、会計導線、締め導線を扱う。後続では営業中一覧ハブとして卓行展開と専用モーダル編集を中心にする。 | カラオケ数量や会計額は操作直後にローカル表示へ即時反映し、保存通信はアプリ内遷移や他フォーム送信の前にまとめて実行する。注文端末から登録された注文はDB保存後の再取得または画面更新で反映する。 |
| 注文端末 | `order-entry` | `/Orders` でopen伝票を選び、注文キューを作って一括登録する。営業中端末の上部タブや業務フローナビには入れず、3パネル横並びの注文入力だけに集中する。画面全体は縦横とも固定し、長い一覧は各パネル本文内でスクロールする。複数台で同時利用できる。 | 注文キューと未送信ドラフトは、店舗・営業日・伝票に紐付けた端末ごとのlocalStorage下書きに保持する。再読込時はDB最新状態で `open` 伝票だけを復元し、登録成功、明示破棄、または伝票状態変更時に削除する。登録成功後のDB/RPC結果を共有状態とし、他端末のローカル下書きとは同期しない。 |

注文端末キューは `/Orders` 端末内の未保存候補であり、DB保存前は会計端末から参照できない。伝票詳細のオーダー追加モーダル内キューも、そのモーダル内の保存前候補であり、注文端末キューとは共有しない。会計前の未保存ブロックは、会計端末がDBまたは自画面状態から直接確認できる未保存に限る。

### 6.2 現場操作性・レスポンス改善の実装状況

現場投入で効果が大きいものは実装済みとする。未実装の追加改善は、後続の検討候補として 6.3 と 14 に分けて扱う。

| 優先 | 状態 | 実装内容 |
| --- | --- | --- |
| 1 | 実装済み | 注文登録、勤怠保存、会計確定、自由入力明細保存では、押下直後に送信ボタンを無効化し、処理中表示を出し、完了または失敗で必ず復帰する。営業中カラオケは保存ボタンを置かず、裏側のAjax保存で同じ復旧方針を満たす。伝票詳細ではカラオケ数量保存操作を持たない。失敗時は入力値とキューを消さず、同じ内容を再送できる。 |
| 2 | 実装済み | `/Orders` と営業中カラオケは「画面内ドラフト」を正式な操作単位にする。追加、数量変更、削除は即座に画面へ反映し、端末内の復旧用状態として扱う。自由入力明細は専用モーダル内の入力状態として扱い、未保存のまま閉じる時は確認して破棄する。端末間の共有状態はDB/RPC保存後のデータを基準にし、端末内ドラフトを他端末へ直接同期しない。 |
| 3 | 実装済み | 登録は必要な単位を1回のPOST/RPCで送る。注文は既存の複数卓キューを維持し、カラオケは商品注文行の数量を伝票単位で一括保存する。自由入力明細は専用モーダルで1件ずつ追加保存し、会計前の追加確認RPCは増やさない。営業中カラオケはアプリ内遷移や他フォーム送信の前に差分を保存し、1タップごとに保存RPCを呼ぶ実装にはしない。 |
| 4 | 実装済み | 候補データは画面初期表示でまとめて渡す。ただし営業中トップの指名候補は初期表示をブロックしないため、伝票追加モーダル表示時にGET handlerで遅延取得する。卓、商品、営業日状態はRazor表示時に取得し、操作中の数量変更では追加RPCを呼ばない。営業中トップは一覧に必要な列だけを取得し、詳細内訳は伝票詳細で取得する。 |
| 5 | 実装済み | マスタ系候補と営業日内候補はサーバー側 `IMemoryCache` に初回成功時だけ保持する。対象は店舗一覧、店舗コンテキスト、卓、キャストマスタ候補、商品候補、商品管理カタログ、キャスト管理一覧、指名バック設定、当日出勤キャスト候補とする。RPC失敗や環境変数未設定の結果はキャッシュしない。商品/カテゴリ保存、商品削除、商品並び順保存、キャスト登録/削除が成功した場合だけ該当店舗の関連キャッシュを破棄する。指名バック設定は現在営業日と同じライフサイクルで保持し、営業日開始、営業日締め、指名バック設定保存の成功時に破棄する。当日出勤キャスト候補の `store.get_order_attending_casts` は店舗別・営業日別に保持し、勤怠保存、退勤情報保存、営業日開始、営業日締めの成功時に破棄する。 |
| 6 | 実装済み | 画面初期表示では既存RPCを保ち、依存しない取得をPageModel内で `Task.WhenAll` により並列化する。新しい集約RPCは作らず、`/`、`/Orders`、`/Slips/Edit` の待ち時間を短縮する。`/Slips/Edit` の出勤キャスト取得は現在営業日の取得完了だけに依存させ、伝票詳細、商品候補、指名種別候補の完了を待たずに開始する。`/Closing` は画面遷移を優先し、各パネルの状態を表示後のJSON handlerで遅延取得する。 |
| 7 | 実装済み | 営業中トップでは締め作業専用の酒代、締め勤怠、未処理領収書、キャスト売上額調整状態を初期取得しない。締め可否判定に必要なデータは `/Closing` の各パネル用JSON handlerで初回表示後、フォーカス復帰、30秒ごとの表示中自動更新で取得する。 |
| 8 | 実装済み | 現在営業日の取得は店舗別に営業日締め成功までキャッシュする。営業日開始時は取得結果で更新し、営業日締め成功時は破棄する。RPC失敗、設定未完了、営業日なしの結果はキャッシュしない。複数インスタンス運用ではプロセス単位のキャッシュになるため、他プロセスで締めた営業日は次回プロセス再起動または明示破棄まで残り得る。 |
| 9 | 実装済み | 一覧RPCは対象営業日・対象伝票を先に絞ってから客、指名、注文、自由入力明細を集計する。`store.get_business_day_slips` と `store.get_cast_sales_adjustment_slips` は全期間集計して最後に絞る形にしない。 |
| 10 | 実装済み | 登録RPCや通常の画面遷移は共通 `AppLoading` で画面操作をロックする。個別画面で重複して二重押し防止を増やすのではなく、共通ロックを通らない独自fetch、部分更新、特殊な遷移処理だけを棚卸し対象にする。 |
| 11 | 実装済み | 営業中カラオケは、アプリ内リンク遷移と他フォーム送信を捕捉して未保存分を `store.save_karaoke_lines` で保存し、成功後だけ遷移または送信を続ける。ブラウザ再読み込みは不要な操作としてF5/Ctrl+Rを抑止し、未保存時の `beforeunload` 警告を出す。 |
| 12 | ソース実装済み（未適用） | 会計確定前に追加の確認RPCは増やさない。`store.issue_checkout_statement` が `checkout_ready` と退店時刻を固定し、`store.confirm_checkout` はその状態、支払方法、預り金、釣銭、支払合計を検証して確定する。画面側の確認スナップショット比較は廃止した。 |

### 6.3 画面/処理別RPC呼び出しとキャッシュ方針

画面遷移や保存処理で実行するRPCは以下を標準とする。マスタ系と現在営業日はアプリサーバーの `IMemoryCache` を使い、伝票、会計、締め可否など営業中に変わる値は原則として最新取得する。RPCごとの結果ライフサイクルは `Docs/SQL_RPC概要.md` の「RPC結果ライフサイクル」に集約する。

| 画面/処理 | 実行するRPC | キャッシュ方針 |
| --- | --- | --- |
| `/` 初期表示 | `store.get_context`, `store.get_current_business_day`, `store.get_tables`。表示後に `BusinessSlips` handlerから `store.get_business_day_slips` | 店舗コンテキスト、現在営業日、卓はキャッシュ対象。営業中一覧はRazor初期表示をブロックせず、初回Ajax、フォーカス復帰、10秒ごとの表示中自動更新で動的取得する。 |
| `/` 伝票作成モーダルの指名候補 | `store.get_current_business_day`, `store.get_order_attending_casts` | 現在営業日と出勤キャスト候補はキャッシュ対象。出勤キャスト候補は店舗別・営業日別に保持し、勤怠保存、退勤情報保存、営業日開始、営業日締めで破棄する。 |
| `/` 伝票作成POST | 画面再表示用ロードとして `store.get_context`, `store.get_current_business_day`, `store.get_tables`, 指名ありの場合は `store.get_order_attending_casts`。保存で `store.create_slip` | マスタ、現在営業日、出勤キャスト候補はキャッシュ対象。保存後の営業中一覧はページ表示後の `BusinessSlips` handlerで取得し、POST直後に `store.get_business_day_slips` を同期再取得しない。 |
| `/` カラオケ遷移時保存 | `store.save_karaoke_lines` のみ | `businessDayId`, `slipId`, `quantity` を画面状態から送信し、対象営業日・対象店舗・open伝票・数量の検証とカラオケ商品行への集約は保存RPC側で行う。店舗コンテキスト、卓、伝票一覧の再取得は不要。 |
| `/Orders` 初期表示 | `store.get_context`, `store.get_current_business_day`, `store.get_order_items`, 営業日がある場合は `store.get_order_attending_casts`。表示後に `SlipOptions` handlerから `store.get_order_entry_slips` | 店舗コンテキスト、現在営業日、商品候補、出勤キャスト候補はキャッシュ対象。注文対象伝票はRazor初期表示をブロックせず、初回Ajax、フォーカス復帰、10秒ごとの表示中自動更新で動的取得する。 |
| `/Orders` 注文登録POST | 保存で `store.add_order_lines`。画面再表示用ロードとして `store.get_context`, `store.get_current_business_day`, `store.get_order_items`, `store.get_order_attending_casts` | 商品候補、出勤キャスト候補、現在営業日はキャッシュ対象。注文登録RPCは対象伝票が選択店舗に属し、open状態であることを保存時に確認する。注文登録成功後は注文対象伝票を同期再取得せず、クライアント側の次回 `SlipOptions` 更新で反映する。成功通知には合計登録行数と卓番ごとの登録件数を表示する。候補から消えた伝票は選択と未送信キューから外す。 |
| `/Slips/Edit` 初期表示 | `store.get_current_business_day`, `store.get_slip_detail`, `store.get_order_items`, 営業日がある場合は `store.get_order_attending_casts` | 現在営業日、商品候補、出勤キャスト候補はキャッシュ対象。伝票詳細は客、指名、注文、調整、カラオケ、会計状態を含むため動的取得。 |
| `/Slips/Edit` 客/指名/注文/調整POST | 検証用に初期表示相当を取得し、保存で `store.add_slip_customers`, `store.leave_slip_customer`, `store.update_slip_customer_label`, `store.add_slip_nominations`, `store.add_order_lines`, `store.void_order_line`, `store.save_slip_adjustments` のいずれか | 保存前後の伝票詳細は動的取得。商品候補、現在営業日はキャッシュ対象。伝票詳細ではカラオケ数量保存POSTを持たない。 |
| `/` 会計モーダル | `store.issue_checkout_statement`, `store.get_checkout_statement_print_data`, `store.release_checkout_ready`, `store.confirm_checkout`, `store.get_checkout_receipt_print_data`, `store.cancel_checkout` | 会計伝票出力から会計取消までを営業中トップだけで扱う。会計伝票の `print_data` と会計確認用 `review_data` は端末内印刷状態と分離し、`checkout_ready` でない伝票は会計確定しない。ソース実装済み（未適用）。 |
| `/Attendance` と `/Closing/Attendance` 初期表示 | `store.get_context`, `store.get_current_business_day`, 営業日がある場合は `store.get_business_day_closing_attendance`, `store.get_casts` | 店舗コンテキスト、現在営業日、キャストマスタはキャッシュ対象。勤怠一覧は出勤/退勤保存で変わるため動的取得。 |
| `/Attendance` と `/Closing/Attendance` 保存POST | `store.get_context`, `store.get_current_business_day`, `store.get_business_day_closing_attendance`, `store.get_casts`, 保存で `store.open_business_day` または `store.open_business_day_with_attendance`, `store.save_business_day_attendance`, 退勤ありの場合は `store.save_business_day_closing_attendance` | 営業日開始時は現在営業日キャッシュを更新する。勤怠保存、退勤情報保存、営業日開始、営業日締めの成功時に `store.get_order_attending_casts` の店舗別・営業日別キャッシュを破棄する。 |
| `/Closing` 初期表示 | `store.get_current_business_day` | 現在営業日はキャッシュ対象。画面遷移を優先し、酒代、勤怠、キャスト売上額調整、領収書、未会計件数は初期表示をブロックしない。 |
| `/Closing` パネル状態JSON/締めPOST検証 | 営業日がある場合は `store.get_open_slip_count`, `store.get_business_day_drink_delivery_status`, `store.get_business_day_closing_attendance`, `store.get_business_day_cast_sales_adjustment_status`, 領収書有効時は `store.get_pending_receipts` | 締め可否に関わる件数や状態はキャッシュしない。後続では `store.get_open_slip_count` が `open` と `checkout_ready` を未会計側に含める。パネル状態は初回表示後、フォーカス復帰、30秒ごとの表示中自動更新で取得し、締めPOSTではサーバー側で再取得して検証する。 |

### 10.1 領収書の再試行表記

最初の印刷指示が失敗した場合、端末内通知からの最初の再試行は初回印刷として扱い、紙面に追加表記を出さない。会計確定成功後に成功応答が端末へ届かず初回印刷要求を作れなかった場合も、後で営業中トップから行う最初の物理印刷は初回印刷として扱う。`doPrint` 成功時だけ同じ会計端末のlocalStorageへ `checkout_id` ごとの初回成功記録を残し、記録ありで店員が明示的にもう一度出力する場合だけ紙面へ `再試行` を印字する。成功記録がない、または端末内データが消失した場合は初回印刷として扱い、会計取消時は成功記録と失敗通知を削除する。手動再発行は操作上の呼称であり、紙面に `再発行` は印字しない。この判断は端末内の出力操作だけで行い、DBの印刷状態・印刷履歴には保存しない。

### 10.2 領収書の取引内容

紙面の取引内容は `ご飲食代として` の1行に固定し、商品、自由入力明細、サービス料を列挙しない。領収書用RPCは確定済み明細をサーバー側で検証・集計するが、ブラウザへ返す `print_data` は取引内容、税率別集計、決済、発行者情報だけとする。確定明細自体は会計記録として保存・再現可能に保つ。

### 10.3 領収書の消費税表示

紙面は会計額に加えて `10%対象 ¥<税込額>（内消費税 ¥<税額>）` を印字する。商品、自由入力明細、サービス料を含む税込会計額全額を10%対象額とし、税額はサーバー側で `round(total_amount * 10 / 110)` により円単位へ丸める。領収書用 `print_data` が税率、対象額、税額を返し、ブラウザは再計算しない。

### 10.4 領収書の決済表示

紙面は決済方法ごとに方法名と決済額を別行で出す。複数決済は `現金 ¥5,000`、`クレジット ¥5,000` のように列挙し、`CAT` は `クレジット` と表示する。0円会計は決済行なしで `請求なし 0円` と表示する。現金の預り金と釣銭は会計処理の確認情報であり、紙面と領収書用 `print_data` には含めない。領収書用 `print_data` が決済行を返し、ブラウザは方法名の連結や金額の再配分をしない。

### 10.5 過去会計の領収書再試行

営業日締め後を含む確定済み伝票の検索・再試行一覧は将来候補であり、今回の後続実装範囲には入れない。入口画面、実装時期、検索RPCの契約は未決定とする。実装時は営業日、会計確定日時、卓番、会計額を表示し、取消済み伝票を一覧・再試行対象から除外する。`checkout_id` と `slip_no` は内部管理に留める。

### 10.6 発行者スナップショット

会計確定と同じトランザクションで、発行者情報を `store_checkouts.issuer_snapshot jsonb` へ保存する。値の元は法人名・適格請求書登録番号を `company_master`、店舗表示名・住所・電話番号・ロゴを `department_master` とし、会計確定後のマスタ変更は過去領収書へ反映しない。画面実装前のサンプル値も同マスタへseedする。発行者項目が欠けていても会計確定は止めず、その時点で得られる値を保存する。領収書用 `print_data` はこのスナップショットを返す。既存会計への値補完は行わない。

法人名、登録番号、店舗表示名、住所、電話番号が欠けた場合は、領収書の表示値だけを `未設定` とする。スナップショットの保存値を補完・更新しない。ロゴは必須事項ではないため、空欄または初期サンプルロゴのまま扱う。

### 10.7 本番移行前の税理士確認

適格簡易請求書としての保存項目、紙面表示、税率別集計、再試行運用は、本番移行前に税理士へ確認する。確認前の仕様はテスト運用の前提であり、税務上の最終判断に代えない。

## 13. 主要データフロー

### 会計関連フローの現在実装

本節の旧「後続では」記述のうち、サービス料の命名、会計確定、会計伝票出力と会計準備、領収書印刷は、会計フロー第1段階として**ソース実装済み（未適用）**である。現在の流れは `営業中トップ -> issue_checkout_statement -> checkout_ready -> 端末内会計伝票印刷完了 -> confirm_checkout -> 初回領収書印刷` であり、会計伝票と領収書の手動再発行・会計取消も営業中トップから扱う。旧 `p_confirmed_snapshot`、`p_closed_at` を渡す会計確定、`ReceiptPrintRequest` / `TempData`、`/Slips/Edit` の会計導線は置換済みである。

| フロー | 状態 | 仕様 |
| --- | --- | --- |
| サービス料の会計データ名 | ソース実装済み（未適用） | 商品小計の20%サービス料は消費税とは別の店舗料金である。DB列、RPC JSON、C#モデルは `service_charge_amount` / `ServiceChargeAmount` とし、`service_tax_amount` / `ServiceTaxAmount` を使わない。テスト段階のため旧契約との互換は作らない。 |
| 店舗選択 | 実装済み | `/Settings` -> `store.get_departments` -> Cookie/localStorage保存 -> `ILocalSettingsProvider` が各Repositoryへ店舗IDを供給する。 |
| 伝票作成 | 実装済み | `/` POST -> `EnsureCurrentAsync` -> 営業日自動作成 -> `store.create_slip` -> `/Slips/Edit` へ遷移する。 |
| 注文登録 | 実装済み | `/Orders` または伝票詳細 -> 標準商品の一覧取得 -> 対象伝票を含む注文payload生成 -> Edge Function経由で `store.add_order_lines` を実行する。`/Orders` で複数卓が同じキューに混在する場合は、注文行ごとの `slip_id` で登録する。注文キューは保存前の端末内状態であり、保存RPC側で対象伝票が選択店舗のopen伝票か確認する。カラオケなどのシステム商品は商品一覧にも注文payloadにも含めず、専用RPCで保存する。 |
| 会計確定 | ソース実装済み（未適用） | 営業中トップ -> Edge Function経由で `store.confirm_checkout` を実行する。会計伝票出力で `checkout_ready` と退店時刻を固定しているため、会計確定は支払入力だけを検証する。`open` からの直接確定、退店時刻引数、画面スナップショット引数は持たない。0円会計は決済方法なしの「請求なし 0円」とする。 |
| 会計伝票出力と会計準備 | ソース実装済み（未適用） | 営業中トップから `store.issue_checkout_statement` で会計伝票を出力し、`checkout_ready`、退店時刻、未退店客を固定する。物理印刷状態は同一端末のlocalStorageだけで管理し、未完了では会計確定を無効にする。再印刷は端末保存値を使い、欠落時だけ読み取り専用RPCで復旧する。解除は `store.release_checkout_ready`、会計済み取消は `store.cancel_checkout` を使う。 |
| 会計取消 | ソース実装済み（未適用） | 営業中トップ -> Edge Function経由で `store.cancel_checkout` を実行し、確定済み会計と支払明細を取消して伝票を営業中へ戻す。取消成功時は同一端末の領収書成功記録と失敗通知を削除する。 |
| 領収書印刷 | ソース実装済み（未適用） | 会計確定の成功応答にある `print_data` を同じブラウザからSII Web SDK Serverへ直接印刷する。失敗通知と即時再試行はlocalStorageに残し、確定済み伝票は営業中トップから手動再発行できる。`再試行` は同じ端末での初回印刷成功後に明示再出力した場合だけ印字する。DBに印刷状態、印刷ジョブ、印刷履歴を持たせない。 |
| 営業日締め | 実装済み | `/Closing` POST -> 通常モードでは領収書入力完了を含む画面側条件確認 -> `store.close_business_day` を実行し、DB側でも条件検証して締める。管理者モードでは画面側条件とDB側条件を `p_ignore_closing_requirements` で迂回する。 |
| 領収書入力 | 実装済み | `/Closing/Receipts` -> Driveプレビュー -> DocManagement契約に沿った仕訳payload作成 -> `store.quick_enter_receipt` の `p_journal_payload` として送信し、領収書ステータスを完了にする。未入力領収書は営業日締めのブロック条件とする。 |
