# ProsperApp システム仕様書

作成日: 2026-07-03
対象: ProsperApp 店舗用アプリ
用途: 開発引継ぎ

## 1. 文書の位置づけ

本書は ProsperApp のシステム構成、画面、主要コンポーネント、外部連携、RPC/SQL運用を整理する。業務要件は `Docs/要件定義書.md`、SQL定義とRPCの俯瞰は `Docs/SQL_RPC概要.md`、作業時の最新方針は `HANDOFF.md` を参照する。

状態区分は以下の通り。

| 状態 | 意味 |
| --- | --- |
| 実装済み | 現行コード、DB、または運用設定に実装が確認できる仕様 |
| 一部実装 | アプリ側の処理はあるが、外部側の正式仕様、画面、または運用定義が残っている仕様 |
| 運用方針 | 実装タスクではなく、現行運用や開発時に維持する前提 |
| 後続仕様 | 未実装で、別途仕様定義してから実装する仕様 |
| 検討候補 | 効果や破棄契機を確認したうえで実装判断する改善案 |

## 4. 認証・認可

| 項目 | 状態 | 仕様 |
| --- | --- | --- |
| 認証方式 | 実装済み | Cookie認証を既定schemeとし、Google OAuth設定がある場合はGoogleをchallenge schemeにする。 |
| Google設定不足 | 実装済み | `GoogleDrive:ClientId` または `GoogleDrive:ClientSecret` が不足する場合、Google challengeを開始しない。 |
| 許可判定 | 実装済み | `GoogleAuthOptions.IsAllowed` が `AllowedEmails` と `AllowedDomains` を照合する。 |
| Cookie検証 | 実装済み | Cookie principal検証時にGoogle設定または許可条件を満たさない場合、principalをrejectしてSessionをclearする。 |
| Google token | 実装済み | Google access tokenは認証ticket作成時にSessionの `GoogleDriveAccessToken` へ保存する。 |
| 認可 | 実装済み | `MapRazorPages().RequireAuthorization()` によりRazor Pageを原則認証必須にする。`/Login` はPageModelの `[AllowAnonymous]` で認証前アクセスを許可する。 |
| logout | 実装済み | `/logout` はSessionをclearし、Cookie認証をsign outする。returnUrlはローカルURLのみ許可する。 |

### 6.1 画面UI仕様

| 領域 | 状態 | 仕様 |
| --- | --- | --- |
| 勤怠キャスト追加 | 実装済み | `/Closing/Attendance` のキャスト追加モーダルは、有効キャストをチェックボックス一覧で表示し、複数名を一括で出勤登録できる。既に当日勤怠があるキャストは重複登録しない。 |
| 勤怠時刻選択 | 実装済み | 勤怠入力の出勤時刻は19:00、退勤時刻は24:00をUI初期値にする。時刻選択肢はそれぞれの初期値を中心に前後12時間を表示し、刻みは店舗別マスターの `attendance_minute_step` に従う。24:00以降の時刻はアプリ内では25:00、26:00のように表記する。 |

| 料金・バック用語 | 運用方針 | 会計額へ加算する料金は指名料金、指名時にキャストへ支払うバックは指名バック、商品注文時にキャストへ支払う通常バックはドリンクバック、商品注文バック対象が当該伝票の指名キャストだった場合のバックは担当バックと呼び分ける。 |

| 指名候補キャスト | 実装済み | 指名追加のキャスト候補は、退勤済みかどうかに関わらず、当日出勤キャスト全員を表示する。 |
| 自由入力明細 | 実装済み | 伝票には通常の商品明細とは別枠で、名前と価格を自由入力できる調整明細を専用モーダルから1件ずつ追加できる。商品マスタには登録せず、価格は負値を許容し、当面は税区分や商品売上分類に分解せず会計合計額へ直接加減する。伝票/会計では通常商品とは別の明細グループとして表示する。未保存入力は会計時ではなくモーダルを閉じる時点で確認し、保存せず閉じる場合は破棄する。 |
| `/Orders` 画面構成 | 実装済み | `/Orders` は注文端末専用の独立画面として、上部タブ、業務フローナビ、フッター、マスタ設定、営業中への戻り導線を表示しない。管理者設定は画面右上のボタンとして残す。卓番選択、商品一覧、注文キューを3パネル横並びにし、画面全体は縦横ともスクロールさせず、各パネル本文だけを縦スクロールにする。 |

| バックキャスト候補 | 実装済み | バック対象商品のバックキャスト選択候補は、先頭に「なし」を表示する。「なし」を選んだ注文行にはバックの摘要を付与しない。候補キャストは退勤済みかどうかに関わらず、当日出勤キャスト全員を表示する。 |
| 営業中会計額 | 実装済み | 営業中画面では卓ごとの会計額を常に隠し、画面右下寄りに固定表示する専用オーバーレイボタンに触れている間だけ会計額が見えるようにする。触れていない状態では会計額を静的テキストとして表示しない。 |
| カラオケ簡易入力 | 実装済み | 営業中画面ではカラオケを伝票行の `+` / `-` ボタンで増減できる。数量変更を即時表示し、手動保存ボタンや短周期の自動保存は置かず、アプリ内遷移や他フォーム送信の前に未保存分を保存する。保存成功後だけ遷移または送信を続行し、保存失敗時は操作を止める。伝票詳細ではカラオケを指名料金と同じ自動システム商品として表示し、数量変更や保存操作は置かない。カラオケは1回200円固定で通常の商品小計に含め、サービス料20%の対象にする。同一伝票ではカラオケ注文行を1行に集約し、時刻列は入店時刻に固定する。 |
| 誤卓防止表示 | 実装済み | 伝票詳細と会計モーダルでは、卓番、客名またはラベル、人数、利用時間、合計を同じ位置関係で確認できるようにする。注文追加や会計操作中に対象伝票を見失わないことを優先し、伝票詳細自体を画面共有キューの置き場所として扱わない。 |
| 会計確定前確認 | 実装済み | 会計モーダルでは追加ページを増やさず、確定ボタン周辺に卓番、客数、退店時刻、合計、支払内訳、現金預かり、釣銭を常時表示する。会計確定直前の確認は同じモーダル内で完結させる。 |
| 会計時領収書印刷 | 実装済み | 会計確定時にSII製レシートプリンター向けの領収書印刷要求データを作成する。`ReceiptPrinter:Enabled = true` の場合、会計確定後に営業中トップへ戻ったブラウザが `siiWebSdk.js` の `PrinterManager` 経由で端末ローカルのSII Web SDK Serverへ接続して印刷する。印刷は80mm幅の紙を前提に、店舗名、現在時刻、伝票番号、「ご飲食代として」、会計額、支払い方法、内消費税額を出し、支払方法の `CAT` は「クレジット」として表示する。会計額50,001円以上では収入印紙欄を追加する。印刷失敗、タイムアウト、設定不足でも会計確定は完了扱いとし、失敗した印刷要求は同じブラウザの営業中トップに再印刷待ちとして残す。 |

### 6.1.1 現場端末運用前提

現場運用は、営業中画面を操作する端末1台と、注文入力専用の `/Orders` 端末複数台で行う。

| 端末種別 | 画面モード | 主な役割 | 同期方針 |
| --- | --- | --- | --- |
| 営業中端末 | `sales-management` | 伝票作成、当日伝票一覧、カラオケ簡易入力、会計導線、締め導線を扱う。 | カラオケ数量や会計額は操作直後にローカル表示へ即時反映し、保存通信はアプリ内遷移や他フォーム送信の前にまとめて実行する。注文端末から登録された注文はDB保存後の再取得または画面更新で反映する。 |
| 注文端末 | `order-entry` | `/Orders` でopen伝票を選び、注文キューを作って一括登録する。営業中端末の上部タブや業務フローナビには入れず、3パネル横並びの注文入力だけに集中する。画面全体は縦横とも固定し、長い一覧は各パネル本文内でスクロールする。複数台で同時利用できる。 | 注文キューと未送信ドラフトは端末ごとのlocalStorageに保持する。登録成功後のDB/RPC結果を共有状態とし、他端末のローカルドラフトとは同期しない。 |

注文端末キューは `/Orders` 端末内の未保存候補であり、DB保存前は会計端末から参照できない。伝票詳細のオーダー追加モーダル内キューも、そのモーダル内の保存前候補であり、注文端末キューとは共有しない。会計前の未保存ブロックは、会計端末がDBまたは自画面状態から直接確認できる未保存に限る。

### 6.2 現場操作性・レスポンス改善の実装状況

現場投入で効果が大きいものは実装済みとする。未実装の追加改善は、後続の検討候補として 6.3 と 14 に分けて扱う。

| 優先 | 状態 | 実装内容 |
| --- | --- | --- |
| 1 | 実装済み | 注文登録、勤怠保存、会計確定、自由入力明細保存では、押下直後に送信ボタンを無効化し、処理中表示を出し、完了または失敗で必ず復帰する。営業中カラオケは保存ボタンを置かず、裏側のAjax保存で同じ復旧方針を満たす。伝票詳細ではカラオケ数量保存操作を持たない。失敗時は入力値とキューを消さず、同じ内容を再送できる。 |
| 2 | 実装済み | `/Orders` と営業中カラオケは「画面内ドラフト」を正式な操作単位にする。追加、数量変更、削除は即座に画面へ反映し、端末内の復旧用状態として扱う。自由入力明細は専用モーダル内の入力状態として扱い、未保存のまま閉じる時は確認して破棄する。端末間の共有状態はDB/RPC保存後のデータを基準にし、端末内ドラフトを他端末へ直接同期しない。 |
| 3 | 実装済み | 登録は必要な単位を1回のPOST/RPCで送る。注文は既存の複数卓キューを維持し、カラオケは商品注文行の数量を伝票単位で一括保存する。自由入力明細は専用モーダルで1件ずつ追加保存し、会計前の追加確認RPCは増やさない。営業中カラオケはアプリ内遷移や他フォーム送信の前に差分を保存し、1タップごとに保存RPCを呼ぶ実装にはしない。 |

### 6.3 画面/処理別RPC呼び出しとキャッシュ方針

画面遷移や保存処理で実行するRPCは以下を標準とする。マスタ系と現在営業日はアプリサーバーの `IMemoryCache` を使い、伝票、会計、締め可否など営業中に変わる値は原則として最新取得する。RPCごとの結果ライフサイクルは `Docs/SQL_RPC概要.md` の「RPC結果ライフサイクル」に集約する。

| 画面/処理 | 実行するRPC | キャッシュ方針 |
| --- | --- | --- |
| `/` 初期表示 | `store.get_context`, `store.get_current_business_day`, `store.get_tables`。表示後に `BusinessSlips` handlerから `store.get_business_day_slips` | 店舗コンテキスト、現在営業日、卓はキャッシュ対象。営業中一覧はRazor初期表示をブロックせず、初回Ajax、フォーカス復帰、30秒ごとの表示中自動更新で動的取得する。 |
| `/` 伝票作成モーダルの指名候補 | `store.get_current_business_day`, `store.get_order_attending_casts` | 現在営業日と出勤キャスト候補はキャッシュ対象。出勤キャスト候補は店舗別・営業日別に保持し、勤怠保存、退勤情報保存、営業日開始、営業日締めで破棄する。 |
| `/` 伝票作成POST | 画面再表示用ロードとして `store.get_context`, `store.get_current_business_day`, `store.get_tables`, 指名ありの場合は `store.get_order_attending_casts`。保存で `store.create_slip` | マスタ、現在営業日、出勤キャスト候補はキャッシュ対象。保存後の営業中一覧はページ表示後の `BusinessSlips` handlerで取得し、POST直後に `store.get_business_day_slips` を同期再取得しない。 |
| `/` カラオケ遷移時保存 | `store.save_karaoke_lines` のみ | `businessDayId`, `slipId`, `quantity` を画面状態から送信し、対象営業日・対象店舗・open伝票・数量の検証とカラオケ商品行への集約は保存RPC側で行う。店舗コンテキスト、卓、伝票一覧の再取得は不要。 |
| `/Orders` 初期表示 | `store.get_context`, `store.get_current_business_day`, `store.get_order_items`, 営業日がある場合は `store.get_order_attending_casts`。表示後に `SlipOptions` handlerから `store.get_order_entry_slips` | 店舗コンテキスト、現在営業日、商品候補、出勤キャスト候補はキャッシュ対象。注文対象伝票はRazor初期表示をブロックせず、初回Ajax、フォーカス復帰、30秒ごとの表示中自動更新で動的取得する。 |
| `/Orders` 注文登録POST | 保存で `store.add_order_lines`。画面再表示用ロードとして `store.get_context`, `store.get_current_business_day`, `store.get_order_items`, `store.get_order_attending_casts` | 商品候補、出勤キャスト候補、現在営業日はキャッシュ対象。注文登録RPCは対象伝票が選択店舗に属し、open状態であることを保存時に確認する。注文登録成功後は注文対象伝票を同期再取得せず、クライアント側の次回 `SlipOptions` 更新で反映する。候補から消えた伝票は選択と未送信キューから外す。 |
| `/Slips/Edit` 初期表示 | `store.get_current_business_day`, `store.get_slip_detail`, `store.get_order_items`, 営業日がある場合は `store.get_order_attending_casts` | 現在営業日、商品候補、出勤キャスト候補はキャッシュ対象。伝票詳細は客、指名、注文、調整、カラオケ、会計状態を含むため動的取得。 |
| `/Slips/Edit` 客/指名/注文/調整POST | 検証用に初期表示相当を取得し、保存で `store.add_slip_customers`, `store.leave_slip_customer`, `store.update_slip_customer_label`, `store.add_slip_nominations`, `store.add_order_lines`, `store.void_order_line`, `store.save_slip_adjustments` のいずれか | 保存前後の伝票詳細は動的取得。商品候補、現在営業日はキャッシュ対象。伝票詳細ではカラオケ数量保存POSTを持たない。 |
| `/Slips/Edit` 会計POST | 検証用に初期表示相当を取得し、保存で `store.confirm_checkout` | 会計額と伝票状態は最新値が必要なため伝票詳細は動的取得。会計確定時は画面で確認した `p_confirmed_snapshot` を渡し、RPC内でDB最新状態と比較する。スナップショット不一致、会計済み、対象伝票なしの場合は伝票詳細を再読込し、会計モーダルを閉じずに再確認させる。会計確定後は営業中トップへ戻り、伝票一覧を再取得する。 |
| `/Attendance` と `/Closing/Attendance` 初期表示 | `store.get_context`, `store.get_current_business_day`, 営業日がある場合は `store.get_business_day_closing_attendance`, `store.get_casts` | 店舗コンテキスト、現在営業日、キャストマスタはキャッシュ対象。勤怠一覧は出勤/退勤保存で変わるため動的取得。 |
| `/Attendance` と `/Closing/Attendance` 保存POST | `store.get_context`, `store.get_current_business_day`, `store.get_business_day_closing_attendance`, `store.get_casts`, 保存で `store.open_business_day` または `store.open_business_day_with_attendance`, `store.save_business_day_attendance`, 退勤ありの場合は `store.save_business_day_closing_attendance` | 営業日開始時は現在営業日キャッシュを更新する。勤怠保存、退勤情報保存、営業日開始、営業日締めの成功時に `store.get_order_attending_casts` の店舗別・営業日別キャッシュを破棄する。 |
| `/Closing` 初期表示 | `store.get_current_business_day` | 現在営業日はキャッシュ対象。画面遷移を優先し、酒代、勤怠、キャスト売上額調整、領収書、未会計件数は初期表示をブロックしない。 |
| `/Closing` パネル状態JSON/締めPOST検証 | 営業日がある場合は `store.get_open_slip_count`, `store.get_business_day_drink_delivery_status`, `store.get_business_day_closing_attendance`, `store.get_business_day_cast_sales_adjustment_status`, 領収書有効時は `store.get_pending_receipts` | 締め可否に関わる件数や状態はキャッシュしない。パネル状態は初回表示後、フォーカス復帰、30秒ごとの表示中自動更新で取得し、締めPOSTではサーバー側で再取得して検証する。 |

| `/Closing/DrinkCost` | `store.get_current_business_day`, 営業日がある場合は `store.get_business_day_drink_delivery_status`, 保存で `store.save_business_day_drink_delivery_amount` | 現在営業日はキャッシュ対象。酒代状態は締め可否に影響するため動的取得。 |

| `/Management/Items` | `store.get_item_admin_catalog`, 保存で `store.upsert_item_category`, `store.upsert_item`, `store.delete_item`, `store.reorder_items` | 商品管理カタログと注文商品候補はキャッシュ対象。商品/カテゴリ保存、削除、並び順保存の成功時に商品関連キャッシュを破棄する。 |

現行未実装または条件付きの追加キャッシュ候補は以下に限定して検討する。

| 候補RPC | 状態 | 方針 |
| --- | --- | --- |
| `store.get_slip_detail` | 原則キャッシュしない | 会計額と保存検証の元データなので、詳細画面では最新取得を維持する。キャッシュする場合は伝票単位の全変更で破棄が必要。 |

## 13. 主要データフロー

| フロー | 状態 | 仕様 |
| --- | --- | --- |
| 店舗選択 | 実装済み | `/Settings` -> `store.get_departments` -> Cookie/localStorage保存 -> `ILocalSettingsProvider` が各Repositoryへ店舗IDを供給する。 |
| 伝票作成 | 実装済み | `/` POST -> `EnsureCurrentAsync` -> 営業日自動作成 -> `store.create_slip` -> `/Slips/Edit` へ遷移する。 |
| 注文登録 | 実装済み | `/Orders` または伝票詳細 -> 標準商品の一覧取得 -> 対象伝票を含む注文payload生成 -> Edge Function経由で `store.add_order_lines` を実行する。`/Orders` で複数卓が同じキューに混在する場合は、注文行ごとの `slip_id` で登録する。注文キューは保存前の端末内状態であり、保存RPC側で対象伝票が選択店舗のopen伝票か確認する。カラオケなどのシステム商品は商品一覧にも注文payloadにも含めず、専用RPCで保存する。 |
| 会計確定 | 実装済み | 伝票詳細 -> Edge Function経由で `store.confirm_checkout` を実行し、伝票状態と会計金額を更新する流れへ寄せる。会計確定前に追加の事前確認RPCは増やさず、会計確定RPCへ画面で確認した伝票スナップショットを渡す。RPC内でDB最新状態と厳密比較し、不一致なら確定せず伝票詳細を再読込して会計モーダル内の再確認へ戻す。カラオケや指名料金などのシステム商品も商品小計へ含め、サービス料20%の対象にする。自由入力明細は会計合計額へ直接加減し、通常商品とは別枠で会計に表示する。会計モーダルは追加確認ステップを増やさず、確定ボタン周辺に卓番、客数、退店時刻、合計、支払内訳、現金、釣銭を常時表示する。 |
| 会計取消 | 実装済み | 伝票詳細 -> Edge Function経由で `store.cancel_checkout` を実行し、確定済み会計と支払明細を取消、伝票を営業中へ戻す。客行の退店状態と退店時刻は変更しない。会計に紐づくキャスト売上額調整は削除してリセットし、再会計後に締め作業で再保存する。 |
| 領収書印刷 | 実装済み | 会計確定 -> 領収書印刷データ作成 -> 営業中トップへリダイレクト -> ブラウザからSII Web SDK Serverへ直接印刷する。印刷失敗時も会計確定は完了させ、失敗した印刷要求は同じブラウザのlocalStorageへ再印刷待ちとして残す。営業中トップから再印刷または完了扱いにできる。 |
| 営業日締め | 実装済み | `/Closing` POST -> 通常モードでは領収書入力完了を含む画面側条件確認 -> `store.close_business_day` を実行し、DB側でも条件検証して締める。管理者モードでは画面側条件とDB側条件を `p_ignore_closing_requirements` で迂回する。 |
| 領収書入力 | 実装済み | `/Closing/Receipts` -> Driveプレビュー -> DocManagement契約に沿った仕訳payload作成 -> `store.quick_enter_receipt` の `p_journal_payload` として送信し、領収書ステータスを完了にする。未入力領収書は営業日締めのブロック条件とする。 |
