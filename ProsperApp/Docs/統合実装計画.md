## 3. 変更してはいけない設計境界

以下は実装済み／採用済みの方針であり、通常の改善タスクで再検討しない。

1. 会計は店舗ごとの単一会計端末・同一ブラウザで完結する。未送信注文や印刷待ちを端末間同期しない。
2. DB上の会計状態は `open` → `checkout_ready` → `checked_out` を正とする。会計伝票の物理印刷状態は端末のlocalStorageだけに置き、DBの印刷ジョブ・履歴・状態を増やさない。
3. `checkout_ready` は会計内容を固定する状態であり、注文、客名、メモ、退店時刻、自由明細、指名を含む全編集を止める。変更時は `release_checkout_ready` を先に行う。
4. `confirm_checkout` は `checkout_ready` のみを確定し、`statement_hash`、画面スナップショット、会計確定時の退店時刻入力を持たない。
5. 0円会計は決済明細を作らず、「請求なし 0円」として確定する。
6. サービス料は消費税と別概念とし、`service_charge_amount` を使う。税額・発行者・決済の印字データはサーバー側 `print_data` を正とし、ブラウザで再計算しない。
7. 領収書は確定済み会計・決済・明細・`issuer_snapshot` から再現する。宛名、物理印刷の成否、再発行回数、紙面画像は会計データに保存しない。
8. 顧客名は内部識別子であり領収書へ印字しない。`checkout_ready` と `checked_out` の顧客名は確定値である。
9. 旧RPC／旧JSONキー／既存データの互換は既定で持ち込まない。必要な移行だけを、対象行・手順・検証方法付きの独立タスクにする。

P0適用後、Azure環境と会計端末で次を一連のシナリオとして確認する。結果は成功／失敗だけでなく、対象伝票、RPC応答、端末内状態、復旧手順を記録する。

| 分類 | 必須シナリオ |
| --- | --- |
| 基本会計 | 通常会計、現金・CAT・PAYPAYの複数決済、金額不足・超過のブロック、現金預り・釣銭 |
| 金額境界 | 0円会計、値引きで0円、サービス料計算、税込55,000円以上の収入印紙欄 |
| 会計伝票 | 出力前の最新状態取得、再印刷、localStorage欠落時の復旧、印刷失敗、店員による完了扱い、会計準備解除 |
| 領収書 | 初回印刷、初回失敗後の再試行、成功応答未達後の初回印刷、初回成功後の明示再試行、手動再発行、会計取消後の再発行拒否 |
| 状態保護 | `checkout_ready` 中の全編集拒否、下書き除去、会計取消、通常締め拒否、管理者モードによる締め条件迂回 |

本番運用へ進める前に、適格簡易請求書の保存項目、紙面表示、10%集計、再試行運用を税理士へ確認する。確認前の会計・領収書仕様はテスト運用の前提であり、税務判断の代替にしない。

#### P1確認記録（2026-07-20）

- 対象環境でテスト伝票を作成し、会計伝票出力で `open` から `checkout_ready` へ遷移し、0円会計を「請求なし 0円」として `checked_out` へ確定した。
- 会計伝票・領収書とも、SII Web SDK Serverへ接続できない端末では印刷失敗を画面表示し、店員による完了扱いと領収書再試行待ちの復旧導線が動作した。SII実機での印刷テストは利用者完了申告として記録する。ここで使用したリモート確認端末にはSII Serverがないため、紙面の独立確認はしていない。
- `store.cancel_checkout` は対象環境のテスト会計に対してロールバック付きで実行し、会計IDを返すことを確認した。さらに、確定済み伝票を取消すと伝票が `open`、会計・決済が `cancelled` になり、`get_checkout_receipt_print_data` が `checkout_not_found` で拒否されることを確認した。ブラウザ上の会計取消は自動化環境のネイティブ確認ダイアログで中断したため、実端末でのボタン操作自体は未確認である。
- テスト営業日は管理者モード相当の締め条件迂回で `closed` を確認した。テスト用の確定会計レコードは監査用の状態遷移結果として残している。
- 対象環境でロールバック付きの受入試験を追加実施した。現金・CAT・PAYPAYの3分割決済、現金預りと500円釣銭、決済額不足と預り不足の拒否、サービス料計算、会計準備解除、注文・客・自由明細の編集拒否、通常締めの `checkout_ready` 拒否、値引き後0円会計、確定済み会計からの領収書再生成を確認した。テスト営業日・伝票・会計はロールバックされ、永続行を残していない。
- 領収書用 `print_data` は税込55,200円で55,000円以上になり、レイアウトの境界テストでも55,000円以上だけが収入印紙欄を出すことを確認した。紙面の寸法・改行・日本語は、SII実機での実測記録が必要である。
- 未確認のP1項目は、実端末上の複数決済フォームと取消ボタン、localStorage欠落・端末再読込時の復旧、`checkout_ready` 中の指名・カラオケを含む残りの編集拒否、初回成功応答未達からの初回領収書、SII紙面の実測、および税理士確認である。

### P2: 営業中から会計完了までの事故防止を仕上げる

P1で安定性を確認した後、画面改修は見た目より誤操作防止を優先して以下の順で進める。

1. **営業中一覧ハブを完成させる**
   - 卓行を展開し、客、指名、注文合計、注文件数、自由入力明細合計、会計伝票出力を要約表示する。
   - 客・指名・自由明細の入力は展開行へ密に置かず、専用モーダルまたは小パネルに分離する。注文時刻や内訳は必要時だけ開く。
   - 注文端末の保存済み変更を10秒ポーリング／フォーカス復帰で反映し、会計伝票出力時は最新取得結果で展開行を更新して、再クリックを要求せず処理を続ける。差分通知は後続実装対象である。
   - 見込み売上を、取消以外の伝票の税込・サービス料込み会計額合計として控えめに表示し、一覧と同じ更新契機に載せる。

2. **未保存・操作ロックを棚卸しする**
   - カラオケは遷移・他フォーム送信前に保存成功を確認し、失敗時は遷移を止めて下書きを残す。
   - 注文キューはDB上で伝票が`open`でなくなった時、保存成功時、明示破棄時に消す。端末間では共有しない。
   - 自由明細は専用モーダルの明示保存とし、閉じる時だけ未保存破棄を確認する。
   - 共通画面ロックを通らない独自fetch、部分更新、特殊な遷移を洗い出し、二重送信や遷移中操作の漏れをなくす。

3. **日常画面の一貫性を整える**
   - 統一した戻るUI、モーダルの固定フッター、Enterによる意図しない送信防止、11インチ横置き基準の列幅・折返し・省略表示を整える。
   - 会計・注文モーダルの入力順、金額確認、主要CTA位置を実利用に合わせて見直す。
   - 保存状態は「未保存／保存中／失敗」のように利用者に意味がある状態だけを表示し、不要な常時「保存済み」表示は増やさない。

## 5. 共通実装ルール

- アプリのDB操作はRepository → `ISupabaseRpcClient` → `prosper-rpc` → `store.*` RPC とする。アプリからの直接REST RPC fallbackは作らない。
- RPCを変更するタスクでは、SQL、必要なschema変更、`99_grants.sql`、Edge Function allowlist、Repository、DTO／JSONパース、関連ドキュメントを同時に更新する。
- `json`／`jsonb` 引数はEdge FunctionからJS配列・オブジェクトのまま渡し、二重`JSON.stringify`をしない。
- 店舗スコープ、`security definer` の`search_path`、更新対象IDと`department_id`、内部ヘルパーの非公開をSQL/RPCレビューで確認する。
- 一覧はキャッシュしない。マスタ・現在営業日・当日出勤キャスト候補は成功時だけキャッシュし、既定の破棄契機を守る。失敗・設定未完了の結果はキャッシュしない。
- SQLを実行する変更では、対象環境、適用順、検証、戻し方を残す。DBを変更した後は、実行SQLと現行ドキュメントを同期する。
- 実装後は最低限 `dotnet build --no-restore` と `git diff --check` を実行し、JavaScriptを変更した場合は構文も確認する。環境確認はローカル起動ではなくAzure App Serviceを基準にする。

## 6. 着手順の判断

次に着手すべき順番は次のとおりである。

1. **P0の対象環境確認と会計変更セットの適用計画確定**
2. **P0のDB/RPC・Edge Function・アプリ配備**
3. **P1の実機／会計受入確認と税理士確認**
4. **P2の営業中一覧ハブ・未保存・操作ロックの改善**
5. **P3の締め作業・時刻制約・性能計測**
6. **P4のリファクタリング**
7. **P5の個別新機能**

P0またはP1で契約不一致・印字不備・状態保護漏れが見つかった場合は、P2以降を進めず、原因をSQL/RPC・Repository・UI・端末状態のどこに置くべきか整理して会計変更セットとして修正する。
