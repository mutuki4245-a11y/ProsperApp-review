## 3. 変更してはいけない設計境界

以下は実装済み／採用済みの方針であり、通常の改善タスクで再検討しない。

1. 会計は店舗ごとの単一会計端末・同一ブラウザで完結する。未送信注文や印刷待ちを端末間同期しない。
2. DB上の会計状態は `open` → `checkout_ready` → `checked_out` を正とする。会計伝票の物理印刷状態は端末のlocalStorageだけに置き、DBの印刷ジョブ・履歴・状態を増やさない。
3. `checkout_ready` は会計内容を固定する状態であり、注文、客名、メモ、退店時刻、自由明細、指名を含む全編集を止める。変更時は `release_checkout_ready` を先に行う。
4. `confirm_checkout` は `checkout_ready` のみを確定し、`statement_hash`、画面スナップショット、会計確定時の退店時刻入力を持たない。
5. 0円会計は決済明細を作らず、「請求なし 0円」として確定する。
6. サービス料は消費税と別概念とし、`service_charge_amount` を使う。税額・発行者・決済の印字データはサーバー側 `print_data` を正とし、ブラウザで再計算しない。
7. 領収書は確定済み会計・決済・明細・`issuer_snapshot` から再現する。宛名、物理印刷の成否、再発行回数、紙面画像は会計データに保存しない。
8. 顧客名は内部識別子であり領収書へ印字しない。`checkout_ready` と `checked_out` の顧客名は確定値である。
9. 旧RPC／旧JSONキー／既存データの互換は既定で持ち込まない。必要な移行だけを、対象行・手順・検証方法付きの独立タスクにする。

### P2: 営業中から会計完了までの事故防止を仕上げる

P1で安定性を確認した後、画面改修は見た目より誤操作防止を優先して以下の順で進める。

## 5. 共通実装ルール

- アプリのDB操作はRepository → `ISupabaseRpcClient` → `prosper-rpc` → `store.*` RPC とする。アプリからの直接REST RPC fallbackは作らない。
- RPCを変更するタスクでは、SQL、必要なschema変更、`99_grants.sql`、Edge Function allowlist、Repository、DTO／JSONパース、関連ドキュメントを同時に更新する。
- `json`／`jsonb` 引数はEdge FunctionからJS配列・オブジェクトのまま渡し、二重`JSON.stringify`をしない。
- 店舗スコープ、`security definer` の`search_path`、更新対象IDと`department_id`、内部ヘルパーの非公開をSQL/RPCレビューで確認する。
- 一覧はキャッシュしない。マスタ・現在営業日・当日出勤キャスト候補は成功時だけキャッシュし、既定の破棄契機を守る。失敗・設定未完了の結果はキャッシュしない。
- SQLを実行する変更では、対象環境、適用順、検証、戻し方を残す。DBを変更した後は、実行SQLと現行ドキュメントを同期する。
- 実装後は最低限 `dotnet build --no-restore` と `git diff --check` を実行し、JavaScriptを変更した場合は構文も確認する。環境確認はローカル起動ではなくAzure App Serviceを基準にする。

## 6. 着手順の判断

次に着手すべき順番は次のとおりである。

1. **P0の対象環境確認と会計変更セットの適用計画確定**
2. **P0のDB/RPC・Edge Function・アプリ配備**
3. **P1の実機／会計受入確認と税理士確認**
4. **P2の営業中一覧ハブ・未保存・操作ロックの改善**
5. **P3の締め作業・時刻制約・性能計測**
6. **P4のリファクタリング**
7. **P5の個別新機能**

P0またはP1で契約不一致・印字不備・状態保護漏れが見つかった場合は、P2以降を進めず、原因をSQL/RPC・Repository・UI・端末状態のどこに置くべきか整理して会計変更セットとして修正する。
