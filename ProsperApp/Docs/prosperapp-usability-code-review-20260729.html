結論

現行アプリは「営業中一覧ハブ」に業務導線を集約し、会計前後の事故防止、対象伝票ロック、 保存待ち、締め条件確認をかなり丁寧に扱っている。特に Repository → prosper-rpc Edge Function → store.* RPC の境界と契約テストは強い。 一方で、営業中トップのフロント状態管理が大きく、注文端末・営業中トップの未送信キュー復元、 決済確定ボタンの有効条件、初期表示の見込み売上に、仕様・コード・ドキュメントのずれが残っていた。 2026-07-30に主要なUI/JS項目はローカル実装し、残りはデプロイ後の実端末受入と環境依存E2Eで確認する。

良い点

営業中トップは未保存操作を flushBusinessHomeChanges でまとめ、会計前や画面遷移前に waitForBusinessOperations を通す。会計発行中は対象伝票だけをロックし、発行後の スナップショット取得失敗時も編集不能側へ倒している。

根拠: wwwroot/js/features/business-home.js:1527、 wwwroot/js/features/business-home.js:1627、 wwwroot/js/features/business-checkout.js:282。

締め作業の待ち時間設計が良い

締め画面は営業日shellを先に確認し、その後の会計、酒代、勤怠、キャスト売上、領収書の各パネルを Promise.all で並列取得する。30秒更新とフォーカス復帰更新もあり、現場で状態が古くなりにくい。

根拠: Pages/Closing/Index.cshtml:489、Pages/Closing/Index.cshtml:501、 Pages/Closing/Index.cshtml:523。

RPC境界と検証が一貫している

C#からは ISupabaseRpcClient を通じて Edge Function に投げ、直接PostgREST RPC fallbackを持たない。 rpc-contract.test.mjs はC#呼び出し、Edge allowlist、SQL定義、security definer、 search_path を照合している。

根拠: Infrastructure/Supabase/SupabaseRpcClient.cs、 Tests/rpc-contract.test.mjs。

運用端末向けの画面密度が作られている

営業中カードは状態別ヘッダー、客・指名チップ、会計額トグル、4列から1列へのレスポンシブ、 操作ボタンの固定高さを持つ。注文端末は卓番、商品、キューの3パネルで、管理者設定以外の導線を抑えている。

根拠: Pages/Index.cshtml:38、Pages/Orders/Index.cshtml:40、 wwwroot/css/features/slips.css:2279。

High

注文端末・営業中トップの未送信キュー復元はローカル実装済み

更新後の HANDOFF.md は、注文端末と営業中トップの両方で、未送信キューを 店舗・営業日・伝票に紐付けたlocalStorage下書きとして復元する方針を正としている。 2026-07-30のローカル実装で、order-entry.js と business-home.js に 店舗・営業日単位のlocalStorage保存キー、復元処理、DB最新状態と合わない行の破棄を追加した。 営業中トップは復元後に既存の store.flush_business_home_changes 再送へ戻す。 残りはデプロイ後の実端末再読み込み受入である。

正仕様: HANDOFF.md:28、HANDOFF.md:115、HANDOFF.md:129。
実装確認: wwwroot/js/features/order-entry.js、wwwroot/js/features/business-home.js。
契約テスト: Tests/order-entry-draft-contract.test.mjs、Tests/business-home-draft-contract.test.mjs。

残確認: Azureへ反映後、注文端末と営業中トップで未送信入力を作り、ブラウザ再読み込み後に復元・保存・破棄が 実端末で成立することを見る。

根拠: Pages/Index.cshtml.cs:81、Pages/Index.cshtml:54。
根拠: Sql/store_rpc/09_business_home_snapshot.sql:376、wwwroot/js/features/business-home.js:562。
実画面: / は読み込み表示消失まで約4.1秒、コンソール警告・エラーなし。

残確認: デプロイ後の公開URLで、営業中画面の初期表示が0円ではなく 取得中 になり、 スナップショット取得後に正しい見込み売上へ更新されることを見る。

営業中トップのPageModelとJSが大きく、変更時の確認コストが高い

IndexModel は伝票一覧、編集flush、伝票作成、会計伝票、決済、領収書、会計取消の JSON endpointをまとめて持つ。フロントも business-home.js、business-slip-editor.js、 business-checkout.js の公開APIで密に協調する。現行の集約自体は業務導線に合っているが、 型付きDTOが薄く、JSON契約のズレは契約テストと手動確認に寄りやすい。

Medium

金額の楽観表示がサーバー計算の近似を持っている

正式な料金計算はSQL/RPC側にあり、営業中スナップショットはサーバー計算値を返す。 一方で、営業中トップの楽観表示は通常注文・自由明細・直前スナップショットの料金案を使い、 Math.round(billableSubtotal * 0.20) で会計額を再投影している。 これは体感速度には効くが、将来サービス料率や計算対象が変わると、サーバーと一時表示の差が出やすい。

根拠: CONTEXT.md:91、Sql/store_rpc/09_business_home_snapshot.sql:224、Sql/store_rpc/08_checkout_ready.sql:80。
根拠: wwwroot/js/features/business-home.js:121、wwwroot/js/features/business-home.js:135、wwwroot/js/features/business-home.js:136。

改善案: JSの再投影は「直前サーバー値 + 追加/取消した明細差分」までに寄せ、 サービス料・下限固定・税などの計算ルールはサーバー提供値またはサーバーから返る投影APIに集約する。

良い

  • 営業中一覧は10秒ポーリング、フォーカス復帰、オンライン復帰で更新する。
