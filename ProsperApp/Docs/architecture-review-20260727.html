CANDIDATE 01

未使用の /Slips/Edit moduleを削除する

Strong

Files

Pages/Slips/*（26ファイル）、 wwwroot/js/features/slip-adjustments.js、 slip-customers.js、slip-nominations.js、 slip-orders.js、slip-panels.js

Problem

現行の営業中編集は、business-slip-editor.jsが営業中スナップショットから UIを構築し、Index PageModelの BusinessSlipEditorOperation handlerへ保存する。 /Slips/Editへのリンク、URL設定、fetchは存在せず、伝票作成後もIndexを再表示する。 残ったPageModel、部分Razor、専用JavaScriptは互いにだけ参照し合う孤立moduleであり、 URL直打ち以外の入口がない。前回レポートでこれを現役adapterと評価したのは誤り。 ただし旧ページの注文数量直接訂正は現行UIへ移っておらず、現行操作は取消 + 再追加である。

Solution

Pages/Slips/*と5つの専用JavaScriptを削除し、レイアウトの /Slips判定、旧Editor helper、専用model、文書、テストの旧前提も除去する。 IStoreSlipRepositoryとEdge allowlistから旧ページ専用契約を外し、 完全に不要な get_business_day_slips と get_slip_detail を削除する。 save_order_line_quantities は、数量訂正を取消 + 再追加へ統一する業務方針を 確認できた場合に削除する。共通利用されている cast-select-modal.jsとorder-back-text.jsは残す。 個別変更SQLのうちflush内部から呼ばれるものは削除せず、非公開実装として残す。

Benefits

31ファイル、旧handler、旧binding、旧部分表示という不要なinterfaceが消え、 localityが上がる。以後の調査で現役コードと互換用コードを取り違えず、 営業中一覧ハブのdepthとleverageを正しく改善できる。

Before

  I["Index / business-slip-editor.js"] --> H["Index operation handlers"]
  H --> R["Repository / RPC"]
  S["Slips/Edit route"] --> P["26 Razor / C# files"]
  P --> J["5 page-specific JS files"]
  N["No inbound link / URL config / fetch"] -.-> S

After

flowchart LR
  I["Index / business-slip-editor.js"] --> H["Index operation handlers"]
  H --> R["Repository / RPC"]
  Q["Quantity correction: void + re-add"] --> I

CANDIDATE 02

既存の営業中編集moduleを深くする

Strong

Files

business-home.js、business-slip-editor.js、 Pages/Index.cshtml.cs、IStoreSlipRepository.cs、 SupabaseStoreSlipRepository.cs、 09_business_home_snapshot.sql、 10_business_home_flush.sql、Edge allowlist

Problem

現行UIはスナップショットを取得し、編集操作とカラオケ下書きをキューへ積み、 まとめてflushする構造へ移行済みである。一方、C#とEdgeには旧一覧、旧詳細、 個別編集、単発operationの浅いinterfaceが残る。ブラウザ側も複数の window.prosperBusinessHome*を公開し、editorとcheckoutが内部状態へ直接触れている。

Solution

営業中一覧・編集同期の公開RPCのseamを get_business_day_snapshot と flush_business_home_changesへ縮める。 apply_business_slip_editor_operationと個別変更関数はflushの内部実装として残し、 Edge allowlistとC#の直接呼び出しから外す。ブラウザではbusiness-home moduleが snapshot、projection、queue、flushを所有し、editorはcommand生成adapter、 checkoutは保存待ちと最新化だけを依頼するadapterにする。

Benefits

既に実装されている再送防止、伝票ロック、部分失敗、最新snapshot返却を1つの深いmoduleへ隠せる。 新しい抽象層を増やさずinterfaceを減らすため、depth、leverage、localityが同時に上がる。

Before

  C["Checkout UI"] --> G
  G --> B["business-home.js"]
  B --> P["Index handlers"]
  P --> R["Broad repository interface"]
  R --> X["Snapshot / flush / direct operation / legacy RPCs"]

After

flowchart LR
  E["Editor adapter"] --> B["Deep Business Home module"]
  C["Checkout adapter"] --> B
  B --> P["Thin Index adapter"]
  P --> X["Snapshot + Flush public RPCs"]
  X --> I["Internal operation helpers"]

CANDIDATE 03

SQL配備とRPC契約を1つのmoduleとして扱う

Strong

Files

Infrastructure/Supabase/*Repository.cs、 supabase/functions/prosper-rpc/index.ts、 Sql/store_rpc/*.sql、Docs/*.md

Problem

RPC名と引数のinterfaceがC#、Edge allowlist、SQL、文書に重複する。 調査開始時は、現行DBに会計RPCが適用済みなのに主要文書が「未適用」のままだった。 また新しいsecurity definer関数に既定EXECUTE ACLが残り、schema usageの剥奪だけに依存していた。 現在のSQL適用順インデックスは 09_business_home_snapshot.sql の次を 99_grants.sqlとしており、依存先の 10_business_home_flush.sql と 料金系の11・12を記載していない。

Solution

SQL適用、Edge配備、契約検証、状態記録を1つの配備moduleにまとめる。 今回追加した契約テストとschema全関数への権限剥奪を入口にし、 SQL依存順も自動検証する。文書の配備状態は自動生成または単一台帳へ寄せる。

Benefits

RPC追加・削除のleverageが高まり、allowlist漏れ、旧SQL上書き、権限ドリフトを同じ変更で検知できる。 操作のlocalityが上がり、Gitと実DBの差を追跡しやすい。

CANDIDATE 04

会計端末状態を独立した深いmoduleへ寄せる

Worth exploring

Files

business-checkout.js、sii-checkout-statement-printer.js、 sii-receipt-printer.js、sii-receipt-layout.js

Problem

DB上の会計状態、localStorage上の印刷状態、モーダル状態、支払計算が同じファイルで調停される。 printer adapter自体は分離されているが、端末状態の復旧規則を検証するinterfaceが浅い。

Solution

ADR 0001・0006・0008を維持したまま、端末内印刷記録と会計遷移の調停だけを所有するmoduleを抽出する。 DBへ印刷状態を追加する案ではない。まずブラウザ状態遷移をテスト可能な純粋ロジックとして分ける。

Benefits

印刷失敗、別ブラウザ復旧、0円会計、会計準備解除の組合せをDOMなしで検証できる。 interfaceは狭くなり、printer adapterの交換にも耐えやすい。

CANDIDATE 05

1実装だけのRepository interfaceを再評価する

Speculative

Files

Problem

多くのinterfaceがSupabase実装1つだけを包み、呼び出し元と実装の間に移動コストを増やしている。 一方でPageModelのテスト境界として使う余地があり、一括削除は根拠不足。

Benefits

不要な薄い層を減らしつつ、テスト可能性に効く境界は保持できる。 推測で大量削除せず、depthを上げる対象を選別できる。

Functional and operational gaps

過去営業日の領収書探索

現行の手動再発行は営業中トップの伝票に寄っており、営業日締め後の検索・再発行導線は将来候補のまま。 税務・店舗運用上の必要期間と検索キーを決める必要がある。

プロセスローカルキャッシュ

MemoryCacheは単一インスタンスでは合理的だが、Azureを複数インスタンス化すると営業日やマスタの 無効化が共有されない。スケール方針を明記するか分散無効化が必要。

配備状態の文書ドリフト

調査開始時は、DBに現行会計RPCが存在する一方、CONTEXTと複数仕様書が未適用と記載していた。 今回は修正済みだが、手動で複数文書を更新する構造が原因であり、単一状態記録への集約が必要。

ブラウザ業務状態のテスト深度

現在のNodeテストは契約・レイアウト・ソース構造の回帰に強いが、 モーダル遷移と失敗復旧の動的な組合せ検証は薄い。Candidate 02と04の後に補強する。

注文数量訂正の業務方針

旧 /Slips/Edit は数量の直接保存を持つが、現行モーダルは注文取消と再追加を使う。 監査上も取消 + 再追加へ統一するなら旧RPCを削除できる。直接訂正が必要なら、 旧ページを残さず現行operation contractへ明示的に追加する。

Decision

追加調査で、/Slips/Editは現行UIのadapterではなく、 URL直打ちでのみ到達可能な孤立moduleだと確認した。最初に31ファイルと連鎖する旧契約を削除する。 注文数量訂正は、取消 + 再追加へ統一するかを確認して削除範囲を確定する。 その後は新しいmoduleを足さず、既存のsnapshot + flush境界を公開interfaceとして深くし、 単発operationと個別変更関数を内部実装へ隠す。Checkout Terminalは別moduleのまま保つ。
