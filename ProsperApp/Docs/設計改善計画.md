# 設計改善計画

## 目的

営業中から会計完了までの実装は動作範囲が広く、PageModel、Razor、ブラウザJS、Repository、RPCの役割が混ざりやすい状態です。今後の修正で同じ不具合を繰り返さないように、問題点、変更方針、実装順をこの文書に固定します。

## 実装状況（2026-07-20）

会計フロー第1段階のソース実装は完了しています。`/` の営業中一覧から会計伝票出力、`checkout_ready`、端末内印刷状態、会計確定、領収書初回印刷・手動再発行、会計取消を扱い、`/Slips/Edit` の会計handler・partial・JavaScriptは削除しました。SQLと `prosper-rpc` allowlistも更新済みです。

未完了なのはリモートDBへのSQL適用、Edge Functionデプロイ、実機プリンターを含む結合確認です。本書のフェーズ0〜4はこのソース実装の完了記録であり、フェーズ5の環境適用・確認は別途対象環境を確認して実施します。

## 問題点

### 1. PageModelに業務変換が残っている

会計確定前の合計計算、確認スナップショットJSON、領収書印刷要求の組み立てが `Pages/Slips/Edit.Checkout.cshtml.cs` にありました。PageModelは画面入力、検証結果、遷移を扱うだけに寄せたい一方で、会計データの形を作る実装も抱えていました。支払行の既定化、退店時刻合成、現金受取額検証も同じPageModelに残っていました。

この状態だと、会計RPCの確認データと印刷データを別々に直してしまい、同じ会計内容を違う形で扱うリスクがあります。

### 2. 注文キューの処理順が呼び出し側に漏れている

`/Orders` と伝票詳細のオーダー追加では、POSTされたJSONをパースし、必要なら既存入力へ戻し、正規化し、業務検証する順序がPageModel側に散っています。

JSONパースと正規化が別の浅い関数として見えているため、呼び出し側が順序を誤ると、空キュー、重複行、バック対象キャストの扱いが画面ごとにずれる可能性があります。自由入力明細も同じく、単一入力の正規化と検証の順序がPageModel側に残っていました。指名追加でも、指名種別マスタ、出勤キャスト候補、指名料金の検証がPageModelに残っていました。客追加、退店、客名更新でも、時刻合成、入力整形、対象客検証がPageModelに残っていました。

### 3. 営業中トップの状態処理が大きい

営業中トップは一覧差分更新、カラオケ未保存状態、伝票作成モーダル、再印刷待ちなどを同じ画面に持っています。現状の方針は妥当ですが、今後の修正では、状態の読み書き単位を小さくしないと、カラオケ保存や再印刷待ちのような端末内状態が他の画面操作に影響しやすくなります。

### 4. レシート印字レイアウトがブラウザ実装へ寄っている

SII Web SDK Serverへの接続自体はブラウザの責務ですが、印字文字列の整形までJSに寄りすぎると、将来のプリンター差し替えや実機別調整時に比較しづらくなります。接続と印字データ整形を分ける余地があります。

## 変更方針

- DB保存、店舗スコープ、会計確定の厳密な一致確認はRPC側に残します。
- アプリ内だけで完結する変換は、不要なadapterや抽象化を増やさず、深いmoduleへ寄せます。
- PageModelは、画面入力、ModelState、Load、Redirect、TempDataに集中させます。
- JSONB/JSON配列の正規化は、呼び出し側へ手順を散らさず、入口moduleに集約します。
- JSの整理は、画面の操作保証が変わらない範囲で、状態管理と外部接続を分ける順に進めます。
- 変更ごとに `dotnet build --no-restore` と `git diff --check` を通します。JS変更を含む場合は構文確認も追加します。

## 会計フロー第1段階の実装の芯

会計伝票出力で対象伝票を `checkout_ready` に固定し、固定済みの退店時刻と支払入力だけで会計確定する流れを中心に実装しました。営業中一覧ハブだけを会計画面として、この状態遷移とRPC契約を同じ実装単位にしています。

営業中一覧ハブを会計の唯一の導線として実装しました。卓行から会計伝票出力、会計準備中表示、再印刷、会計準備解除、支払入力による会計確定までを完結させ、会計成功後の同じブラウザで行う領収書印刷とも接続します。`/Slips/Edit` には会計画面、復旧画面、会計用端末キューを持たせません。

`checkout_ready` への遷移は、物理プリンターの成功ではなく、サーバー側の会計伝票出力RPCが成功した時点で確定します。SII印刷失敗、タイムアウト、端末側設定不足があってもDB状態は戻さず、会計準備中のまま再印刷または会計準備解除で対応します。

通常の営業日締めでは `open` と `checkout_ready` の両方を未会計伝票として数え、1件でもあれば締めを拒否します。管理者モードの締め条件無視は既存どおりこの条件を迂回します。

会計準備解除の成功応答時も、対象伝票の同一端末の会計伝票印刷記録をlocalStorageから削除します。解除後の伝票内容は変更可能になるため、解除前の会計伝票を再印刷させません。

会計準備解除は追加確認ダイアログを出さない通常操作とします。解除RPCは `checkout_ready` の伝票だけを `open` に戻し、`store_slips.closed_at` と `left_at_source = 'accounting_slip'` の客行退店時刻だけを未確定へ戻します。`left_at_source = 'manual'` の個別退店登録は消しません。

旧 `store.confirm_checkout(p_closed_at, p_confirmed_snapshot)` は互換用に残さず、`store.confirm_checkout(p_department_id, p_slip_id, p_payments, p_received_amount)` へ一括切り替え済みです。`open` 伝票から直接会計確定できる経路は残さず、DB/RPCとアプリ側呼び出しを同じ実装単位で更新しています。戻す場合もSQLだけ、またはアプリだけを戻さず、会計RPC契約と呼び出し側を同時に戻します。

会計内容を変える更新RPCは、`store_slips.status = 'open'` の伝票だけを対象にします。注文追加、注文数量訂正、注文取消、指名追加、自由入力明細追加/削除、客追加は、`checkout_ready` の伝票ではRPC側で拒否します。会計準備中の客名、メモ、個別退店時刻も同様に変更できません。顧客名は注文端末や締め時のキャスト売上額調整一覧で伝票を識別する内部情報であり、領収書の宛名には使いません。現行は会計済み伝票の客名だけを後修正できる例外を持ちますが、後続では `open` の伝票だけを更新対象にして、`checkout_ready` と `checked_out` では確定値として扱います。画面側の非表示やdisabledは補助であり、状態保護の正はRPC側に置きます。

`checkout_ready` の伝票は、締め条件や未会計数では会計済みではない伝票として扱います。ただし営業中一覧では通常の `open` 伝票とは分け、「会計準備中」として表示し、編集不可、再印刷、会計準備解除、会計確定へ進む状態を明示します。

会計伝票印字データは公開RPCごとに再実装せず、SQL側の内部用ヘルパーに集約します。後続実装では `store.build_checkout_statement_data(...)` のようなgrantしない内部関数を作り、`store.issue_checkout_statement` と `store.get_checkout_statement_print_data` は同じヘルパー結果を使います。

会計伝票のヘッダは `department_master.department_name` の店舗表示名、卓番、入店時刻、退店時刻、`customer_count` とし、注文端末や締め時の内部識別である顧客名、指名キャスト名・種別、バック対象キャスト、`checkout_id`、`slip_id`、`slip_no` は `checkout-statement-v1` の表示項目と紙面へ含めません。`customer_count` は会計伝票発行時点の `store_slip_customers.status <> 'cancelled'` の件数を使い、途中退店客は含めます。

`store.issue_checkout_statement` と `store.get_checkout_statement_print_data` は、紙面用の `print_data jsonb` と会計確認用の `review_data jsonb` を返します。`print_data` は `schema_version = 'checkout-statement-v1'` を持つ会計伝票印字用JSONであり、`review_data` は会計確認画面だけに使います。旧 `ReceiptPrintRequest` は削除済みで、会計伝票は客確認用、領収書は `checkout-receipt-v2` の別 `print_data` として分離します。

会計伝票の物理印刷は、既存のSII Web SDK Server接続、エラー表示、再印刷待ちの扱いを再利用できる形にします。ただし印字レイアウトは領収書用 `sii-receipt-layout.js` へ分岐追加せず、`checkout-statement-v1` 用の会計伝票レイアウトとして分けます。プリンター接続層は共通、紙面レイアウト層は会計伝票と領収書で分離します。

営業中端末は店舗1台で、会計準備中の伝票を別端末から変更しない運用を前提にします。そのため、`store.issue_checkout_statement` が返した `print_data` は、物理印刷を開始する前に同一ブラウザの会計伝票用 `localStorage` キューへ保存し、成功後は直ちに物理印刷を開始します。同じ端末での印刷失敗・再印刷はこの保存済みデータを使い、通常は追加RPCを呼びません。キュー項目は `slip_id` を識別子にし、端末内で `印刷待ち`、`印刷中`、`印刷失敗`、`印刷済み` を表します。端末内印刷状態は会計確定を無効にせず、会計準備中のモーダルで再印刷、会計準備解除、決済への移行を選べるようにします。端末記録は会計確定の成功応答時に削除し、記録がない `checkout_ready` は `store.get_checkout_statement_print_data` を再印刷用に1回呼んで復旧します。これはDB状態を増やさない端末内UI状態であり、`checkout_ready` は会計準備中を表す唯一のDB状態とします。会計確定そのものは `checkout_ready` から `checked_out` へ遷移するDB操作であり、端末状態にはしません。会計確定の成功応答を受けた時だけ領収書印刷要求を作成し、失敗時には領収書印刷や再印刷待ちを作りません。DB上の `checkout_ready` は状態と会計確定の正であり、localStorageは再印刷レスポンスを改善するための印刷データ保持に限定します。営業中一覧の10秒更新にも印刷用JSONを含めません。

領収書の最初の印刷は会計確定の成功応答後だけに開始する。`store.confirm_checkout` の成功応答に初回印刷用の領収書 `print_data` を含め、その値を直接印刷する。領収書日付は確定会計の `checkout_at` を店舗時刻へ変換した実日付とし、退店時刻や営業日を流用しない。`checkout_id`、`slip_id`、`slip_no` は端末内の対象特定とRPC契約の内部識別子であり、領収書の表示項目・紙面へ含めない。直後の印刷失敗は同一ブラウザのlocalStorageで通知・即時再試行できるが、これは業務状態ではない。`checked_out` の確定済み伝票は営業中トップからいつでも手動再発行できる。`store.get_checkout_receipt_print_data` は手動再発行用に、確定済み伝票、会計、決済、明細、会計確定時の発行者スナップショットを領収書用 `print_data jsonb` に1回で組み立てる読み取り専用RPCとする。初回応答と手動再発行RPCは同じ内部SQLヘルパーを使い、伝票詳細取得へ会計・決済を混ぜず、画面側で領収書データを組み立て直さない。紙面に `再試行` を印字するのは、同じ端末の初回印刷成功記録があり、店員が明示的に再出力する場合だけである。宛名は初回印刷・再発行時の任意入力とし、会計データに保存しない。領収書の `pending`、`sent`、`failed`、印刷履歴をDBテーブルや `store_slips.status` に持たせず、会計取消済み伝票は再発行対象から除外する。本番化までに、適格簡易請求書の必要事項を確定済み会計・決済・明細と会計確定時の発行者スナップショットから再現できるようにする。課税対象は商品、自由入力明細、サービス料を含めて10%固定とし、税込会計額を10%対象額として扱う。複数税率の税区分・集計は別タスクに分ける。

### 領収書の再試行表記

手動再発行用 `store.get_checkout_receipt_print_data` は、紙面用の `print_data` とは別に端末内の初回成功記録キー用 `checkout_id` を返す。初回会計確定の成功応答も同じ `checkout_id` を返すため、IDを顧客向け紙面に含めず同一端末の出力区分を判定できる。

初回印刷失敗後の最初の再試行は初回印刷として追加表記なしで出力する。会計確定成功後に成功応答が端末へ届かず初回印刷要求を作れなかった場合も、後で営業中トップから行う最初の物理印刷は初回印刷として扱う。`doPrint` 成功時だけ同じ会計端末のlocalStorageへ `checkout_id` ごとの初回成功記録を残し、記録ありで店員が明示的にもう一度出力する場合だけ `再試行` を紙面へ印字する。成功記録がない、または端末内データが消失した場合は初回印刷として扱う。会計取消時は成功記録と失敗通知を削除する。手動再発行は操作名であり、紙面に `再発行` は印字しない。判定は端末内の出力操作に限定し、DBの印刷状態・履歴を増やさない。

### 領収書の取引内容

顧客向け紙面は `ご飲食代として` の1行だけを取引内容として出し、商品、自由入力明細、サービス料を列挙しない。領収書用RPCは確定済み明細をサーバー側で検証・税率別に集計するが、ブラウザへ返す `print_data` に明細配列を含めない。確定明細は会計記録として保存・再現可能に保つ。

### 領収書の消費税表示

紙面は会計額とは別に `10%対象 ¥<税込額>（内消費税 ¥<税額>）` を印字する。商品、自由入力明細、サービス料を含む税込会計額全額を10%対象額とし、税額は領収書用RPCが `round(total_amount * 10 / 110)` で円単位に丸める。ブラウザで税額を再計算しない。

### 領収書の決済表示

紙面は決済方法ごとに方法名と決済額を別行で出す。複数決済は `現金 ¥5,000`、`クレジット ¥5,000` のように列挙する。0円会計は決済行なしで `請求なし 0円` とし、現金の預り金と釣銭は会計確認用に留めて紙面と `print_data` に含めない。

### サービス料の計算対象

サービス料は有効な `store_order_lines` 全体の小計に20%を掛け、`round(order_subtotal_amount * 0.20)` とする。標準商品、カラオケ、指名料金を含み、自由入力明細の加算・値引きはサービス料の対象に含めない。`base_amount = order_subtotal_amount + service_charge_amount`、`applied_adjustment_amount = max(adjustment_amount, -base_amount)`、`total_amount = base_amount + applied_adjustment_amount` とする。計算上の合計が負でも会計伝票出力・会計確定を拒否せず、0円会計として会計伝票と領収書を出力する。超過した値引きを繰り越し・印字しない。

### 固定決済方法の初期化

現金、CAT、PAYPAYの固定3行は専用seed SQLで `payment_method_master` に事前作成する。後続の会計RPCは固定3方法の有効行を参照・検証するだけで、マスタをinsert/updateしない。現行の会計ごとのupsertは削除し、マスタ管理画面・取得RPCは別タスクに分ける。

### 発行者スナップショット

会計確定と同じトランザクションで、法人名、適格請求書登録番号、店舗表示名、住所、電話番号、ロゴを `store_checkouts.issuer_snapshot jsonb` へ値コピーする。値の元は法人名・登録番号を `company_master`、店舗表示名・住所・電話番号・ロゴを `department_master` とする。画面実装前のサンプル値も同マスタへseedする。領収書用RPCは現在のマスタをjoinせず、この会計時スナップショットを返す。既存会計への値補完や旧契約の互換は作らない。

発行者項目が欠けても会計確定は止めない。法人名、登録番号、店舗表示名、住所、電話番号が空なら、保存値を補完せず紙面上だけ `未設定` と明示する。ロゴは必須項目ではないため、空欄または初期サンプルロゴのままとする。

本番移行前に、適格簡易請求書としての保存項目、紙面表示、税率別集計、再試行運用を税理士へ確認する。確認前の仕様はテスト運用の前提であり、税務上の最終判断に代えない。

## 会計フロー第1段階の実装記録

### 達成済みの完了条件

営業中一覧ハブの展開卓行から、会計伝票出力、同一端末での印刷完了確認、会計確定、初回領収書印刷までを完結できることを第1段階の完了とする。`/Slips/Edit` を会計に使わないことも完了条件に含む。DB上の状態は `open`、`checkout_ready`、`checked_out` だけであり、印刷待ちなどの状態や印刷履歴をDBへ追加しない。

### フェーズ0: 契約を固定する（ソース実装完了）

- 現行の `store.confirm_checkout`、会計取消、営業日締め、伝票更新RPC、SII印刷要求の入出力を一覧化し、新旧契約の置換箇所を確定する。
- 現行の `p_closed_at`、`p_confirmed_snapshot`、`service_tax_amount`、会計ごとの決済方法upsert、ブラウザ側の領収書金額・発行者情報組み立てを削除対象として明示する。
- 既存行への値補完や旧RPC/JSONキーの互換は作らない。SQL実行・本番反映はこの計画に含めず、実装と確認後に別途判断する。

### フェーズ1: SQL/RPCを一つの移行単位で更新する（ソース実装完了・リモート未適用）

1. スキーマとseedを更新する。
   - `store_slips.status` に `checkout_ready`、`store_slip_customers.left_at_source`、`store_checkouts.issuer_snapshot`、発行者マスタ列を追加する。
   - `service_tax_amount` を `service_charge_amount` へ改名し、現金・CAT・PAYPAYの固定決済方法と発行者サンプル値をidempotentにseedする。
2. 状態保護と締め条件を更新する。
   - 会計内容を変えるRPCと顧客名更新を `open` 限定にし、`open` と `checkout_ready` の両方を未会計として締め判定する。
3. 会計伝票・領収書の内部SQLヘルパーを作る。
   - `store.build_checkout_statement_data(...)` と領収書用の内部ヘルパーを公開せず、各公開RPCから共通利用する。
4. 公開RPCを切り替える。
   - `store.issue_checkout_statement`、`store.get_checkout_statement_print_data`、`store.release_checkout_ready`、新契約の `store.confirm_checkout`、`store.get_checkout_receipt_print_data` を揃える。
   - `confirm_checkout` は `checkout_ready` だけを確定し、会計ID・釣銭・初回領収書 `print_data` を返す。手動領収書RPCは `checkout_id` と `print_data` を別に返す。
   - 会計取消時は同一端末の領収書成功記録・失敗通知を消せる識別子を返す。
5. `01_business_day.sql`、`05_checkout.sql`、`99_grants.sql` を同じ変更単位で整合させ、公開RPCのgrantと内部ヘルパー非公開を確認する。

### フェーズ2: C#の契約と会計画面部品を先に揃える（ソース実装完了）

- Repositoryとモデルを新RPCの応答へ追随させ、会計伝票用と領収書用の `print_data` モデルを分ける。
- `CheckoutDocumentBuilder` の確認スナップショット・ブラウザ計算由来の領収書データを廃止し、PageModelは入力、エラー、遷移だけを扱う。
- 会計画面部品を営業中一覧ハブに置き、退店時刻、支払入力、0円会計、確定可否をこの画面だけで実装する。

### フェーズ3: 印刷と端末内状態を実装する（ソース実装完了）

- 会計伝票専用レイアウトとlocalStorageキューを実装する。`印刷待ち`、`印刷中`、`印刷失敗`、`印刷済み` を再印刷用に管理し、会計伝票出力後は直ちに物理印刷を開始する。印刷状態は確定条件にせず、欠落時は再印刷用の復旧RPCで再作成する。
- 領収書はサーバー返却の `print_data` だけで印字し、発行者情報・税額・決済額をブラウザで再計算しない。`checkout_id` と `slip_no` は紙面に出さない。
- `doPrint` 成功時だけ `checkout_id` の初回成功記録を残す。記録ありの明示出力は `再試行`、記録なし・応答未達・端末データ消失時の最初の物理印刷は初回扱いとする。

### フェーズ4: 営業中一覧ハブを主導線として接続する（ソース実装完了）

- 展開卓行に会計伝票出力、会計準備中表示、再印刷、会計準備解除、支払入力、会計確定を接続する。
- 10秒更新とフォーカス復帰で `checkout_ready` を通常の編集中伝票と区別して反映し、印刷用JSONは一覧更新へ含めない。
- `/Slips/Edit` に会計導線を置かず、会計準備中の復旧、再印刷、会計確定も営業中一覧ハブだけで扱う。

### フェーズ5: 検証・分割・引継ぎ（静的確認完了・環境適用待ち）

- SQL/RPCの引数、戻り列、店舗スコープ、`security definer` とgrantを静的に照合する。SQLを実行する場合は対象環境と順序を別途確認する。
- `dotnet build --no-restore`、`git diff --check`、変更したJavaScriptの構文確認を通す。
- 少なくとも、通常会計、複数決済、0円会計、値引きで0円、会計伝票印刷失敗と復旧、会計準備解除、初回領収書失敗、成功後の再試行、応答未達後の初回出力、会計取消、`checkout_ready` 中の更新拒否、営業日締め拒否を確認する。
- SQL/RPC、C#、Razor/JSを別コミットに分ける。DB適用はGit revertだけでは戻らないため、適用順と戻し方を引継ぎへ残す。

### この段階から外すもの

- 発行者マスタの編集画面、画像ロゴ、複数税率・非課税、過去会計の検索・再印刷一覧、決済方法マスタの管理UIは別タスクとする。
- 税理士確認は本番移行の条件であり、テスト段階の実装完了条件には含めない。

## 別タスクのリファクタリング候補

以下は会計フロー第1段階の完了条件には含めない。会計フローが安定してから、必要なものを独立して実施する。

- 会計の `CheckoutDocumentBuilder`、`CheckoutInputEditor`、`ReceiptPrintRequest`、`TempData` を介した旧経路は削除済みです。会計伝票と領収書の印字データはSQLの `print_data` を正とし、PageModelはJSON handlerの入力検証と応答だけを扱います。
