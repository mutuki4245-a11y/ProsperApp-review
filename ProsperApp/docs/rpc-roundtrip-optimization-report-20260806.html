ProsperApp RPC 往復最小化レポート

全画面・画面内操作・自動更新・キャッシュを静的に追跡し、体感速度を上げるための集約RPCを優先順位つきで提案する。

調査日: 2026-08-06 / 対象: Razor Pages、JavaScript、Application Service、Supabase Repository、Edge Function、Sql/ 定義 / 実DB・ネットワークは未実行

1 経路全DBアクセスは Edge Function 経由の RPC。PostgREST のテーブルREST直呼びは確認されなかった。
10 秒営業中トップと注文候補のポーリング間隔。営業中一覧は full snapshot を再取得する。
30 秒稼働中キャッシュ、領収書待ち一覧、締めトップ更新の基準。各値の意味は異なる。
最優先 3 件勤怠保存の原子化、締めダッシュボード集約、会計変更結果への snapshot 同梱。

結論

最も効果が大きいのは、読み込みを短いTTLで増やすことではなく、書込みの「検証読取 → 複数書込み → 再読込」を1トランザクションRPCの応答へ置き換えることです。 すでに flush_business_home_changes はブラウザ操作を1バッチに集約できています。同じ原則を勤怠、締めダッシュボード、会計後の一覧更新、領収書次件遷移に広げます。
P0

勤怠 bundle

キャスト/スタッフの出退勤、営業日自動開始、結果一覧を1 RPCにする。現在は条件次第で複数連続往復。

P0

締め dashboard

強制current取得、readiness、任意の領収書件数を単一read modelにする。30秒ごとの2〜3往復を1往復へ。

P0

会計 mutation + snapshot

会計発行・解除・確定・取消の結果に最新snapshotを付け、直後の一覧再取得をなくす。

数え方と対象範囲

本レポートの「RPC回数」は、アプリサーバーから prosper-rpc Edge Function へ送るHTTP POST数です。SQL関数がSQL内部から別関数を呼ぶ回数、ブラウザ→RazorのHTTP、Google Drive APIは別に記載します。0〜1 はプロセス内キャッシュのhit/missで変動し、N は入力件数またはバッチ内操作数に依存します。

提案する集約RPCと優先順位

以下は変更案です。新関数はすべて既存の認可・RLS・Edge Function許可リスト・監査/会計ガードを同等に満たすことを前提とします。特に勤怠・会計・領収書は業務上の原子性を高める提案であり、SQL適用前に競合・再送・戻し方を設計します。

P0 / 最大効果

store.save_business_day_attendance_bundle

用途: 勤怠画面の保存。p_expected_business_day_id、キャスト/スタッフの出勤・退勤入力を受け、営業日がなければ開始し、楽観的競合を検証して全行を1トランザクションで保存する。結果として business day、正規化済みattendance一覧、件数、revisionを返す。

現状

代表 4〜8+ RPC
提案後
画面GETで得たrevisionを添えて bundle 1回。成功応答で画面を更新するか、締めへ遷移する。
保存本体 1 RPC

置換対象: get_current_business_day、open_business_day[_with_attendance]、4種類のattendance save、保存直後のget_business_day_closing_attendanceを、保存時の往復から外す。

必須ガード: 既存の時刻刻み・営業日・キャスト/スタッフ存在・closed day不変・再送idempotencyをDB側で検証し、失敗時も部分保存しない。業務ロジック変更なので、先にテストとロールバックSQLを用意する。

P1

store.create_slip_and_snapshot

伝票作成時に、営業日存在確認/必要なら開始、伝票・顧客・指名作成、最新snapshotを1トランザクションで返す。ブラウザをAJAX化し、POST前後のget_store_bootstrapを消す。

効果: 既存営業日で 3〜4 → 1、営業日なしで 5 → 1（表示更新を応答で行う場合）。卓・候補マスタは初期GETのcacheを使い、作成レスポンスに再送しない。

P1

領収書用 read/write context: get_receipt_entry_context / quick_enter_receipt_and_next

前者は current business day、出勤キャスト候補、pending一覧/現在・次件を1回で返す。後者は入力保存後に残件数と次件コンテキストを返す。必要な会社IDはSQL側でdepartmentから解決できるため、アプリ側のget_context missも外せる。

効果: 「次へ」は事前Load、context読取、pending再読込、redirect先GETの重複を除き、保存操作を 6〜9 → 1〜2 に近づける。画面をSPA化しない場合でも、write応答のnext IDを使ってPRG後の再読込を1回に限定できる。

実装注意: accounting journal payloadの組立責務をSQLへ移すかは別の会計設計判断。まずは既存payloadを維持して「次件context返却」だけを追加する段階案が安全。

P1

マスタ mutation の応答を正とする（新しい巨大RPCは不要）

upsert_table、create_cast、upsert_item、save_pricing_plan_v2などの成功応答を、更新後recordまたは対象一覧・revisionまで拡張する。アプリは対象cacheを直接更新し、同一リクエスト内のbootstrap再読込をやめる。

効果: 典型的な write 1 + bootstrap 1 = 2 → 1。全マスタを返す共通mutate_masterより、既存RPCのバージョンアップの方が権限・検証・エラー意味を保ちやすい。

P2 / 応答時間

flush_business_home_changes 内の中間snapshotを除去する

ブラウザ→EdgeのHTTP回数はすでに1回である一方、SQLはbatch内の各editor operationでapply_business_slip_editor_operation→snapshotを生成し、flush終了時にももう一度snapshotを生成する。クライアントが使うのは最終snapshotなので、内部関数はoperation resultのみ返し、flushで最終1回だけsnapshotを構築する。

効果: RPC回数は不変、SQL計算・JSON転送は操作数Nに比例して減少。これは営業中編集のp95を下げる優先最適化。

P2 / payload

get_business_home_bootstrap_v2 を画面専用に縮小する

営業中トップが必要とするのは context、営業日、卓、指名、商品、出勤キャスト、決済、snapshotである。現在のget_store_bootstrapは部署、卓/キャスト/スタッフの管理一覧、商品管理catalog、料金planまで同時に返す。画面専用read modelは1往復のまま、SQL仕事量とHTML初期payloadを削減できる。

P2 / ポーリング

revisionベースの差分配信を段階導入する

営業中snapshotには既に business_day_revision があり、JSも単調増加を扱っている。まず known_revision を受け取り「変更なし」を小さく返す契約にしてpayload/SQLを減らす。これは呼数自体は減らさないため、呼数を減らす最終段階は SignalR/SSE または認可済みRealtimeで「他端末更新時だけ再取得」へ移すことになる。

ポーリングを止める前に、接続切断時の再同期・可視状態・端末複数台・revision欠番をテストする。

実施順序と成功指標

  1. P0-1 勤怠bundle: 現行保存ケースを入力組合せ（キャストのみ/スタッフのみ/両方/営業日なし/退勤あり/競合/再送）で固定し、SQLとPageModelを置換する。
  2. P0-2 締めdashboard: 既存readiness JSONと同等の表示を新read modelで返し、30秒更新を1 endpointにする。
  3. P0-3 会計mutation+snapshot: 解除→確定→取消を1操作1RPC応答でUIに反映し、直後の一覧fetchを外す。
  4. P1: 伝票作成、領収書次件、マスタmutation応答を順に移す。各段階で旧handlerとの二重実行を避ける feature flag を置く。
  5. P2: flush SQL内部の余分なsnapshotを除去し、専用bootstrapとrevision配信を測定にもとづいて導入する。
