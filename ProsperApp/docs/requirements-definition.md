# ProsperApp 要件定義書

作成日: 2026-07-30

対象: 現行 `main` 実装を正とした ProsperApp の業務要件・機能要件。

注記:

- 本書はコード、SQL、Edge Function、画面実装、契約テストから確認できる仕様を整理したもの。
- 環境ごとの秘密値、接続先URL、APIキー、publish profileの内容は記載しない。
- 実際に利用できる機能は `App:EnabledFeatures`、Supabase、Google、プリンタ、店舗マスタなどの本番設定に依存する。

## 1. 目的

ProsperApp は、店舗営業における日次業務を一つのWebアプリで扱うためのシステムである。主な対象業務は、営業日の開始、勤怠入力、伝票作成、営業中の注文・会計、領収書簡易入力、締め前確認、営業日締め、店舗マスタ管理である。

本システムは、店舗スタッフが営業中に素早く操作できること、締め時に未処理を残さないこと、会計時点と締め時点の金額・状態を後から追えることを重視する。

## 2. 利用者と端末

### 2.1 店舗スタッフ

- 営業中画面で伝票、顧客、指名、注文、自由入力明細、カラオケ、会計を操作する。
- 勤怠入力、酒代入力、キャスト売上額調整、領収書簡易入力、締め作業を行う。
- 店舗設定画面で、キャスト、商品、指名バック、時間料金のマスタと端末の画面モード・配色を管理する。

### 2.2 注文端末スタッフ

- 注文端末画面で open 状態の伝票を選択し、商品を注文キューに追加して一括登録する。
- 端末設定で画面モードが注文端末に設定されている場合、営業中画面へのアクセスは注文端末画面に誘導される。

### 2.3 管理担当者

- 管理者設定画面で端末の利用店舗、キャッシュ、デバッグ削除を管理する。

## 3. 前提・制約

- アプリ画面は認証済みユーザーだけが利用できる。
- Google OAuth が設定されている場合、許可メールアドレスまたは許可ドメインのユーザーだけがログインできる。
- 店舗は端末ごとのローカル設定 `StoreDepartmentId` で選択する。
- 営業日は店舗単位で管理し、営業日の切替基準は日本時間の正午 12:00 とする。
- DB 操作は ASP.NET Core アプリから Supabase Edge Function `prosper-rpc` を経由して、許可済みの PostgreSQL RPC だけを実行する。
- ローカルサーバー起動や Azure App Service への直接デプロイは、本書の作成範囲には含めない。

## 4. 機能要件

### FR-01 認証・認可

- すべての Razor Pages は、ログイン画面を除き認証を必須とする。
- Google OAuth のクライアント設定がある場合は Google ログインを利用する。
- Google 認証では、`GoogleAuth:AllowedEmails` または `GoogleAuth:AllowedDomains` のいずれかでアクセス制限を必須とする。
- 許可されていないユーザー、または設定が不足している状態では、利用者をログインまたはエラー表示へ誘導する。
- ログアウト時は認証 Cookie と Session を破棄する。

### FR-02 機能フラグ

- 以下の機能は `App:EnabledFeatures` で有効化を制御する。
  - Opening
  - Slips
  - Orders
  - Checkout
  - Closing
  - Receipts
  - Settings
- 機能フラグが無効なページは NotFound とする。

### FR-03 端末設定

- 端末ごとに以下を保存できる。
  - 利用店舗
  - 画面モード
  - 配色テーマ
- 設定は Cookie と localStorage に保持する。
- 利用店舗は、パスワード保護された管理者設定画面で変更する。
- 画面モードと配色テーマは店舗設定画面で変更する。
- 画面モードは営業管理画面と注文端末画面を切り替える。
- 配色テーマは暗色テーマと白テーマを切り替える。

### FR-04 営業日管理

- 店舗ごとに現在営業日を取得できる。
- 現行仕様では、現在営業日が存在しない場合、勤怠入力の保存時に営業日を作成する。
- 過去営業日が未締めの場合、新しい営業入力はブロックする。
- 営業日は `open`、`closed`、`cancelled` の状態を持つ。
- 営業日を締めるには締め条件をすべて満たす必要がある。

### FR-05 勤怠入力

- 出勤対象キャストを検索・選択できる。
- 出勤時刻、退勤時刻、送り利用の有無を入力できる。
- 出勤時刻は必須とし、退勤時刻がある場合は出勤後でなければならない。
- 時刻候補は店舗設定の分単位に従う。
- `/Attendance` と `/Closing/Attendance` は同じ勤怠入力機能を利用する。
- 締め導線から保存した場合は締め作業へ戻る。

### FR-06 伝票作成

- 営業中画面から新しい伝票を作成できる。
- 伝票作成時に入力する主な項目は、卓番、入店時刻、共有メモ、顧客名、指名区分、指名料金、指名キャストである。
- 伝票作成には、卓番、入店時刻、1名以上の顧客、出勤キャストが必要である。
- 顧客数は 1 から 20 名までとする。
- 顧客名は 100 文字以内、共有メモは 500 文字以内とする。
- 入店時刻は 5 分単位の候補から選択し、未来すぎる時刻または過去 2 日を超える時刻は不可とする。
- 指名料金は 1,000 円から 20,000 円まで、1,000 円単位とする。
- 伝票作成時は同一キャストの重複指名を不可とする。

### FR-07 営業中画面

- 営業中画面では、見込み売上、未会計数、会計済み数、営業日を表示する。
- 伝票は `open`、`checkout_ready`、`checked_out`、`cancelled` の状態を持つ。
- 画面上のフィルタで、すべて、接客中、会計準備、会計済みを切り替えられる。
- 伝票カードには、卓番、入店時刻、人数、在席時間、状態、顧客、指名、会計額を表示できる。
- 会計額はツールバーのトグルで表示・非表示を切り替えられる。
- 営業日スナップショットは定期更新、画面復帰時、手動再取得で更新する。
- 営業中画面ではブラウザの更新操作による未送信データ消失を防ぐ。

### FR-08 伝票詳細・営業中編集

- 伝票詳細では、伝票サマリー、顧客、指名、注文、自由入力明細、カラオケ、会計内訳を確認できる。
- `open` 状態の伝票では以下の編集ができる。
  - 顧客追加
  - 顧客名変更
  - 顧客退店
  - 指名追加
  - 指名取消
  - 注文明細追加
  - 注文明細取消
  - 自由入力明細追加
  - 自由入力明細取消
  - カラオケ回数変更
- 編集内容は端末の localStorage に店舗・営業日単位で下書き保存する。
- 編集は楽観表示後に `flush_business_home_changes` で一括保存する。
- flush は `client_batch_id` により冪等に処理する。
- 保存失敗した行は画面上で失敗として扱い、利用者が再操作できるようにする。
- `checkout_ready` 以降の伝票は営業中編集不可とする。

### FR-09 注文端末

- 注文端末画面では、現在営業日の `open` 伝票だけを選択できる。
- 商品はカテゴリ別のボタンとして表示する。
- 伝票未選択時に商品を押した場合は、先に卓番を選択するよう案内する。
- 注文は端末内キューに追加され、一括登録で保存する。
- 注文キューは店舗・営業日単位で localStorage に保存し、登録成功後に破棄する。
- 伝票が `open` でなくなった場合、その伝票向けの未登録キュー行は自動で除外する。
- バック対象商品では、指定なしまたは出勤キャストを選択できる。
- 同一伝票・同一商品・同一バック対象の注文は数量を合算する。

### FR-10 会計

- `open` 伝票は会計伝票発行により `checkout_ready` になる。
- 会計伝票発行時に、時間料金、注文、指名料、自由入力明細、税額、印字データ、レビュー用データを固定する。
- `checkout_ready` 伝票では、会計伝票の再印刷、会計準備解除、決済確定ができる。
- 会計準備解除時は固定済み会計スナップショットと自動料金明細を無効化し、伝票を編集可能状態へ戻す。
- 決済確定時は、会計準備時に固定した合計金額を基準にする。
- 決済金額の合計は会計額と一致しなければならない。
- 受取額が必要な決済方法では、受取額が決済額以上でなければならない。
- 決済方法は DB の決済方法マスタに従う。
- 会計額が 0 円の場合は、決済なしで確定できる。
- 会計確定後は領収書印字データを取得できる。
- 会計取消時は、会計、決済、会計スナップショット、関連する売上調整を無効化する。

### FR-11 印刷

- 会計伝票と領収書は SII Web SDK Server 連携で印刷する。
- プリンタ連携の有効化、SDK URL、WebSocket host、コードページ、行幅は設定で制御する。
- 領収書印刷に失敗した場合、端末の再印刷待ちキューに残す。
- 利用者は再印刷待ち領収書を再印刷、または完了扱いにできる。
- 明示的な再印刷では再発行であることが分かる印字データを扱う。
- 領収書合計が印紙判定金額以上の場合、収入印紙欄を出力する。

### FR-12 締め作業

- 締め作業画面では、締め条件の状態をカード表示する。
- 締め条件は以下とする。
  - 未会計伝票が 0 件
  - 酒代が入力済み
  - 勤怠が 1 名以上
  - 退勤未入力が 0 件
  - 必要なキャスト売上額調整が完了
  - 領収書機能が有効な場合、未処理領収書が 0 件
- 締め条件は 30 秒ごと、画面復帰時、手動再取得で更新する。
- すべての条件を満たした場合だけ営業日締めを実行できる。
- 締め時は営業日締めスナップショットを保存する。
- 締め後は対象営業日の伝票、注文、会計、勤怠、料金明細、会計スナップショットなどを更新不可とする。

### FR-13 酒代入力

- 営業日の酒代納品額を整数円で保存できる。
- 営業日が未作成の場合、先に勤怠入力で営業日を作成する。
- 0 円も入力済みとして扱う。
- 保存後は締め作業画面に戻る。

### FR-14 キャスト売上額調整

- 会計済みかつ指名関連キャストが存在する伝票を対象に、キャスト別の売上額を入力できる。
- 初期値は店舗設定の売上額基準と分配方法に従う。
- 分配方法は、全額配賦または分割配賦を扱う。
- 分割配賦では、時間ベースの推奨額が利用できる場合はそれを優先し、利用できない場合は均等配分を用いる。
- 伝票単位の保存と、営業日単位の一括確認保存ができる。
- 必要な全伝票の調整が完了した場合、締め条件を満たす。

### FR-15 領収書簡易入力

- 領収書機能が有効な場合、未処理領収書を一覧順に処理できる。
- Drive ファイルが紐付く証憑は、許可された未処理領収書に限りプレビューできる。
- 入力項目は、支払日、金額、科目、摘要、グループコードである。
- 支払日は当日から過去 1 年以内とする。
- 金額は整数円とする。
- 科目は画面で定義されたカテゴリと明細の組み合わせから選択する。
- 摘要は必須とする。
- 保存時は仕訳 payload を生成し、領収書を処理済みステータスに更新する。
- スキップにより次の証憑へ進める。
- スキャンミスとして対象外ステータスに変更できる。

### FR-16 マスタ管理

- 店舗スタッフは、店舗設定画面で以下を管理できる。
  - キャスト
  - 商品カテゴリ
  - 商品
  - 指名バック
  - 時間料金
- 店舗設定画面で端末の画面モードと配色テーマを変更できる。
- キャストは追加、削除、ドリンクメモ編集ができる。
- 商品カテゴリはコード、名称、表示順、有効状態を管理できる。
- 商品はカテゴリ、名称、価格、有効状態、バック対象、通常バック額、指名バック額を管理できる。
- 商品は表示順を変更できる。
- 指名バックは指名区分ごとのバック単価と有効状態を管理できる。
- 時間料金はセット時間、セット料金、延長料金、有効状態を管理できる。
- 削除操作は原則として論理削除として扱う。

### FR-17 管理者設定

- 管理担当者は、管理者設定をパスワード解除後に操作できる。
- 解除後の保存操作にはセッション上の保存トークンを要求する。
- 利用店舗を端末設定として保存できる。この保存では店舗設定画面で選択した画面モードと配色テーマを維持する。
- アプリ内メモリキャッシュを全削除できる。
- 確認文字列が一致した場合だけ、非マスタデータ削除を実行できる。
- 非マスタデータ削除はデバッグ用途とし、本番運用では慎重に扱う。

## 5. データ整合性要件

- 伝票編集の一括保存は、同一 `client_batch_id` の再送を安全に扱う。
- 同一 `client_batch_id` に異なる内容を再利用した場合は拒否する。
- 会計準備時点で、会計額と印字データを固定する。
- 決済確定時は会計準備時の固定スナップショットを基準とし、現在時刻で再計算しない。
- 営業日締め時点で、営業日全体の締めスナップショットを固定する。
- 締め後の対象営業日データは DB トリガで更新不可とする。
- DB の公開ロールから `store` schema の直接実行権限を剥奪し、アプリは Edge Function 経由の許可済み RPC だけを使う。

## 6. 非機能要件

### 6.1 セキュリティ

- アプリ画面は認証を必須とする。
- Google 認証を利用する場合は、許可メールまたは許可ドメインを必須とする。
- Supabase RPC は Edge Function の API キー照合を通過したリクエストだけを処理する。
- DB の RPC は `security definer` と固定 `search_path` を前提とする。
- 秘密情報は設定または環境変数で管理し、リポジトリや仕様書に含めない。

### 6.2 可用性・劣化時動作

- Supabase RPC が未設定または利用不可の場合、画面は読み込み問題として表示し、保存処理は失敗を返す。
- Google Drive 認証が必要な証憑プレビューでは、トークンがない場合にログインへ誘導する。
- 印刷失敗時も会計確定済み領収書は再印刷待ちとして端末に保持する。

### 6.3 性能

- マスタ系データは 10 分キャッシュする。
- 営業中など短期変動データは 30 秒キャッシュする。
- Drive プレビューは 10 分キャッシュする。
- 営業中画面と締め画面は定期更新と画面復帰時更新により、手動更新なしで状態を追従する。

### 6.4 操作性

- 営業中画面は伝票カード中心で、状態別フィルタと詳細モーダルにより操作する。
- 注文端末はナビゲーションを省いた端末表示とし、卓番選択、商品選択、キュー確認を一画面で扱う。
- 会計や領収書などの重要操作は大型モーダルで入力内容を確認する。
- localStorage 下書きにより、営業中編集と注文キューの途中状態を端末内に保持する。

### 6.5 運用・監査

- 契約テストにより、C# 側 RPC 呼び出し、Edge Function allowlist、SQL 定義、権限、重要会計契約の一致を検査する。
- 締め時と会計準備時のスナップショットにより、後から当時の会計・締め状態を確認できる。
- ドキュメントのみの変更はアプリ実行成果物に影響しないため、Azure App Service 直接デプロイ対象外とする。

## 7. 現行対象外・制約事項

- 店舗会社、店舗部門、卓番、決済方法など、一部マスタは画面から編集できない。
- 管理者設定のパスワードはアプリ全体のロール管理ではなく、当該画面操作の解除用途である。
- localStorage の下書きや印刷待ちキューは端末単位であり、他端末へ自動共有されない。
- 実 DB の初期データ、Edge Function のデプロイ状態、Google OAuth 同意状態、SII Web SDK Server の起動状態は、コードだけでは確定しない。
- 領収書 Drive プレビューは未処理領収書に紐付くファイルのみを対象とする。
