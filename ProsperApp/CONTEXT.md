# Domain Context

## 実装状況（2026-07-28）

この文書の会計伝票、`checkout_ready`、会計確定、領収書印刷、営業中編集に関する記述は、営業中トップ `/`、`business-home.js`、`business-slip-editor.js`、`business-checkout.js`、会計伝票・領収書のSII印刷モジュール、Repository、SQLソースとして実装済みである。`/Slips/Edit` は削除済みであり、営業中の編集と会計は `/` の営業中一覧から完結する。

会計変更セットはリモートDB、`prosper-rpc` Edge Function、Azure App Serviceへ適用済みである。P1受入確認とプリンター実機別の印字調整は継続中であり、最新の適用状況は `HANDOFF.md` を参照する。

## Glossary

### 営業フロー

営業中トップで伝票を作成し、営業中一覧の卓行展開や注文端末で注文・調整・指名を扱い、会計完了まで進める一連の現場操作。

### 営業中一覧ハブ

営業中トップの卓一覧を、卓の現在状態確認、客・指名・注文・自由明細の修正、会計伝票出力へ進む中心導線として扱う考え方。展開行は要約を常時表示し、編集は対象ごとの専用モーダルへ分け、注文明細の時刻一覧や内訳は必要時に開く。営業中トップには見込み売上として、取消以外の伝票の会計額合計を参考表示する。見込み売上の会計額は、その時点で計算できる税込・サービス料込みの最終請求額とする。見込み売上は営業中一覧ハブと同じ10秒ポーリング/フォーカス復帰で更新する。営業中一覧・編集同期の公開RPCは `store.get_business_day_snapshot` と `store.flush_business_home_changes` に集約し、個別編集関数はflush内部の実装として扱う。会計伝票出力では、一覧の表示状態ではなく直前に取得した対象伝票の最新保存状態を基準にする。直前取得で差分があった場合は、一覧側を最新化して軽い通知を出し、そのまま最新状態で出力操作へ進む。

### 営業中から会計完了までの優先改善

締め作業と管理画面は後回しにし、営業中トップ、営業中一覧ハブ、注文端末、会計完了までの事故防止を優先する。優先改善は、会計準備中の全編集禁止、カラオケ数量の遷移時保存、自由明細の専用モーダル保存、共通画面ロックから漏れる独自処理の棚卸しに絞る。

### 事故防止

店舗スタッフの操作ミスや見落としによって、売上、伝票状態、保存状態、会計結果が意図しない状態になることを防ぐ考え方。見た目の刷新より優先される。

### RPC・遷移待ちの操作ロック

登録RPCや画面遷移の待機中は、共通の画面ロックで追加操作を防ぐ前提とする。個別画面で重複した二重押し対策を増やすのではなく、共通ロックを通らない独自fetch、部分更新、特殊な遷移処理だけを確認対象にする。

### 会計端末

店舗ごとに1台だけ置き、会計伝票の出力、再印刷、会計確定を一貫して担当する営業中端末。注文端末とは区別し、会計準備中の伝票を別端末へ引き継がない。

### 誤会計

卓番、客数、注文内容、自由入力明細、退店時刻、決済内訳、合計金額のいずれかを取り違えたまま会計を確定すること。

### 誤卓

操作対象の卓番や伝票を取り違えること。伝票詳細や会計モーダルでは、卓番、客名またはラベル、人数、利用時間、合計を常に同じ位置に固定表示し、注文追加や会計操作中も対象伝票を見失わないようにする。

### 未保存

画面上では変更されたように見えるが、DBへ確定保存されていない状態。営業フローでは、未保存状態を利用者に明示し、遷移や確定前に解消する対象として扱う。

### 注文端末キュー

注文端末 `/Orders` 上で、まだ保存されていない注文候補を一時的に保持する端末内の状態。DBへ保存されるまでは他端末から参照できる前提にしない。

### 伝票詳細オーダー追加キュー

伝票詳細のオーダー追加モーダル内で、保存前の注文候補を一時的にまとめる状態。注文端末キューとは別物で、画面全体や他端末に共有されるキューとして扱わない。

### 会計伝票

会計前に印刷し、席で客に注文内容、利用時刻、人数、合計を確認してもらうための伝票。出力時に退店時刻を選択して確定し、直前取得した最新保存状態を元に出力する。オーダー明細は商品名、数量、単価、金額だけのまとめ行で印字し、バック対象キャストと注文時刻一覧は印字しない。自由入力明細は通常オーダーとは別枠で、摘要と符号付き金額だけを個別行として印字する。会計確認画面の注文行には、店員が内部のバック付け先を確認するためバック対象キャストを表示する。合計欄は小計、サービス料、内消費税（10%）、合計の4段表示にし、内消費税は合計に加算しない参考表示とする。支払方法、預り金、釣銭は出さない。会計伝票出力RPC `store.issue_checkout_statement` は、退店時刻確定、会計準備中化、未退店客の補完、印刷データ返却までを1RPCで行う。RPC成功後は直ちに物理印刷を開始するが、その成否は会計確定の条件にしない。会計準備中は同じ内容を自由に再印刷でき、紙面に `再印刷` などの表記や印刷履歴を持たせない。同一端末の再印刷は端末のlocalStorageに保持した `print_data` を使い、端末記録がない場合だけ読み取り専用RPC `store.get_checkout_statement_print_data` で会計準備中の現在DB状態から復旧する。支払方法や預り金ではなく会計内容の確認を目的とする。

会計伝票のヘッダは店舗表示名、卓番、入店時刻、退店時刻、客数だけを出力し、客名、指名情報、バック情報、`checkout_id`、`slip_id`、`slip_no` は印字データの表示項目にも紙面にも含めない。客数は取消客を除く客行数であり、途中退店した客は含める。

### 会計準備中

会計伝票を出力し、客への内容確認から会計処理へ進むために一切の伝票編集を止めている専用の伝票状態。DB上の `store_slips.status` は `checkout_ready` とする。締め条件や未会計数ではまだ会計済みではない伝票として扱うが、営業中一覧では通常の編集中伝票とは分けて「会計準備中」と表示する。プリンター失敗時も状態は維持し、再印刷または会計準備解除で対応する。客名、メモ、個別退店時刻を含め、追加注文や修正が必要な場合は通常操作で会計準備を解除し、`store_slips.closed_at` と会計伝票出力で補完した退店時刻だけを未確定へ戻して、変更後に会計伝票を再印刷する。会計準備解除は `checkout_ready` 専用で、会計済みの `checked_out` は会計取消で扱う。退店時刻は個別退店登録由来の `manual` と、会計伝票出力由来の `accounting_slip` を区別する。

### 顧客名

伝票内で客を識別するための表示名。注文端末や締め時のキャスト売上額調整一覧で使う内部情報であり、領収書の宛名には使わない。顧客名は `open` の伝票だけで変更でき、`checkout_ready` と `checked_out` では確定値として変更しない。訂正が必要な会計準備中伝票は会計準備を解除してから行い、会計確定後は会計取消で営業中へ戻した場合だけ変更できる。

### 会計伝票の印刷待ち

会計伝票を物理印刷する同一端末内のUI状態。DBの伝票ステータスには追加せず、会計伝票用localStorageの `印刷待ち`、`印刷中`、`印刷失敗`、`印刷済み` で表す。出力操作はRPC成功後に直ちに印刷を開始し、失敗しても会計準備中のまま再印刷、会計準備解除、決済への移行を選べる。端末内の印刷状態は会計確定の許可条件に使わない。記録は会計確定の成功応答時に削除する。記録がない `checkout_ready` は、再印刷用に復旧用RPCから会計伝票を取得する。

`store.release_checkout_ready` の成功応答時も、対象伝票の同一端末の会計伝票印刷記録を削除する。解除後に伝票内容を変更できるため、解除前の会計伝票を再印刷させない。

通常の営業日締めでは `open` と `checkout_ready` の両方を未会計伝票として扱い、1件でもあれば締めを拒否する。管理者モードの締め条件無視は既存どおりこの条件も迂回できる。

### 会計処理

会計伝票で確認済みの内容に対して、支払方法、現金預り金、釣銭、決済確定を扱う操作。明細確認は会計処理の中で繰り返さない。`store.confirm_checkout` は会計準備中の `checkout_ready` 伝票だけを受け付け、`open` 伝票から直接会計確定しない。退店時刻は会計伝票出力時に固定した `store_slips.closed_at` を使い、会計確定時には再入力しない。RPCは `checkout_ready` と固定済み退店時刻、支払合計、預り金を検証する。複数決済の入力額は利用者の入力を尊重し、初回選択時の残額初期入力以外で自動上書きしない。確定時に合計一致を画面で確認する。

### 0円会計

会計額が0円の伝票を、支払を発生させずに会計として確定する扱い。自由入力明細を含む計算上の合計が負になった場合も、会計額を0円へ下限固定して同じ扱いにする。会計伝票と領収書は0円で出力し、画面や領収書の支払方法欄では「請求なし 0円」のように表示する。支払方法別の売上集計へ0円決済明細を混ぜず、余った値引きを繰り越さない。超過した値引きは会計伝票・領収書に出さない。

### 固定決済方法の初期化

会計改修の初期実装では、決済方法を現金、CAT、PAYPAYの3種類に固定する。`payment_method_master` の3行は専用のidempotentなseed SQLで事前作成し、`store.confirm_checkout` はマスタをinsert/updateしない。会計RPCは同一店舗の有効な固定方法だけを検証して使い、マスタ管理画面・取得RPCは別タスクとする。

1会計で同じ決済方法は1行だけとし、`store.confirm_checkout` は入力された決済方法コードの重複を拒否する。画面の1方法1行という制約だけに依存しない。

### サービス料の計算対象

サービス料は、有効な `store_order_lines` と自動料金明細の合計に20%を掛け、`round((order_subtotal_amount + pricing_subtotal_amount) * 0.20)` で円単位へ丸める。標準商品、カラオケ、指名料金、セット料金、延長料金を含み、自由入力明細の加算・値引きだけはサービス料の計算対象に含めず、サービス料計算後にそのまま加減する。`base_amount = order_subtotal_amount + pricing_subtotal_amount + service_charge_amount`、`applied_adjustment_amount = max(adjustment_amount, -base_amount)`、`total_amount = base_amount + applied_adjustment_amount` とする。超過した値引きは繰越さず、会計伝票・領収書の印字データへ含めない。

### 料金プラン・自動料金明細

店舗ごとのセット・延長料金を決める設定を料金プランと呼ぶ。標準プラン `set_extension_v1` は、セット時間、1人時のセット・延長単価、複数人時の1人あたりセット・延長単価を持つ。入店時点の人数でセット料金を1回計算し、セット終了ちょうどから同じ間隔で延長料金を発生させる。各料金イベントでは入店時刻を含み、退店時刻を含まない在席人数を使う。自由数式や動的SQLは料金プランに含めず、店舗固有の料金制度は同じ入力・出力契約を満たす名前付き料金実装として追加する。

料金計算モジュールは「伝票・計算基準時刻」から自動料金明細案、適用料金プラン版、小計を返すサーバー側の唯一の計算口である。営業中一覧では現在時刻までの案だけを全伝票スナップショットに含め、ブラウザ側で時間料金を再計算しない。案は `set_fee` / `extension_fee` のシステム商品形式でも明細に含める。会計伝票出力時には選択した退店時刻で計算した自動料金明細とプラン版を `store_slip_pricing_lines` に固定保存し、対応する編集不可の `store_order_lines`（`source_type = automatic_pricing`）を生成する。料金計算明細が監査上の正本であり、システム商品行は帳票・明細表示と既存の注文集計へ載せるための対応行である。会計準備中の再印刷・決済は固定済み明細を使い、会計準備解除後に再出力した場合だけ、その時点の料金プランで改めて計算する。標準プランではキャストへ帰属させない。

### サービス料

商品小計に対して加算する店舗料金。現行ソースでは20%であり、消費税とは別物である。確定会計、RPC、C#モデルの金額は `service_charge_amount` / `ServiceChargeAmount` と呼び、消費税を意味する `service_tax_amount` / `ServiceTaxAmount` は使わない。テスト段階のため旧列・旧JSONキーとの互換は作らない。

### 会計確定前の未保存ブロック

会計確定前にブロック対象とする未保存は、会計端末がDBまたは自画面状態から直接確認できるものに限る。別端末の注文端末キューなど、DBへ保存されていない端末内状態は対象外とする。

### 端末内下書き

未送信の注文キューと営業中カラオケ数量は、端末ごとのlocalStorage下書きとして保持し、画面再読込後にも復元する。下書きは店舗・営業日・伝票に紐付け、復元時にはDBの最新状態と照合する。対象伝票が `open` でなくなった、保存に成功した、または利用者が明示破棄した場合は削除する。下書きは端末間で同期せず、DB保存前の業務事実として扱わない。

### 会計確定後の印刷失敗

会計確定と領収書印刷は分けて扱う。会計確定を先にDBへ保存し、印刷失敗によって支払い済み伝票を未会計へ戻さない。印刷失敗の端末内通知は再試行の補助であり、会計や領収書の業務状態ではない。

### 領収書印刷失敗の端末通知

最初の領収書印刷が失敗した場合だけ、同一ブラウザのlocalStorageに印刷失敗通知と印刷要求を残し、その場で再試行または完了扱いにできる。これはDBへ保存しない端末内の補助情報であり、消失しても会計済み伝票の手動再発行を妨げない。会計取消が成功した場合は同じ端末の通知を削除し、取消済み会計は手動再発行も受け付けない。

### 領収書

会計確定の成功応答を受けた後だけ最初の印刷要求を作る支払証憑。会計確定自体は `checkout_ready` から `checked_out` へ遷移するDB操作であり、端末状態ではない。`store.confirm_checkout` は成功応答に初回印刷用の領収書 `print_data` を含め、その値だけを最初の印刷に使う。宛名はこの `print_data` に含めず、会計画面で入力した任意値を印刷時にだけ重ねる。`checkout_id`、`slip_id`、`slip_no` は端末内の対象特定やRPC引数に使う内部識別子であり、領収書の表示項目や紙面には出さない。成功応答がない場合は領収書印刷要求も端末内通知も作らない。`checked_out` の伝票は営業中一覧からいつでも手動で再発行できる。手動再発行では、読み取り専用RPC `store.get_checkout_receipt_print_data(p_department_id, p_slip_id)` が確定済み伝票、会計、決済、明細、会計確定時の発行者スナップショットを1回で領収書用 `print_data jsonb` に組み立て、端末用の内部応答値として `checkout_id` も返す。通常の伝票詳細を会計・決済情報で肥大化させず、画面側で領収書の構成を再実装しない。手動再発行の紙面には、同じ端末で初回印刷成功記録がある場合だけ `再試行` を印字する。宛名は初回印刷・再発行時の任意入力であり、会計データに保存しない。領収書の `pending`、`sent`、`failed` などをDB状態、伝票状態、印刷ジョブテーブルとして管理しない。日付は `store_checkouts.checkout_at` を店舗時刻へ変換した会計確定の実日付を印字し、選択した退店時刻 `store_slips.closed_at` と営業日は内部管理用として扱う。深夜営業で営業日と暦日がずれる場合も、領収書の発行日は実日付を優先する。

### 領収書の出力区分

最初の印刷指示が失敗した場合、その端末通知から行う最初の再試行は初回印刷として扱い、紙面に追加表記を出さない。会計確定は成功したが成功応答が端末へ届かず、初回印刷要求を作れなかった場合も、後で営業中トップから行う最初の物理印刷は初回印刷として扱う。同じ会計端末では、`doPrint` 成功時だけ `checkout_id` ごとの初回印刷成功記録をlocalStorageへ残す。記録ありで店員が明示的にもう一度出力する場合だけ、紙面へ `再試行` を印字する。`再試行` として始めた出力が失敗した場合も、以後の再試行はすべて `再試行` 表記を維持する。成功記録がない、または端末内データが消失した場合は初回印刷として扱う。会計取消が成功した場合は、この成功記録と失敗通知を削除する。ここでいう手動再発行は操作上の呼称であり、紙面の `再発行` 表記は使わない。この区分は端末内の出力操作だけで決め、DBの印刷状態や印刷履歴には保存しない。

### 領収書の取引内容

顧客へ渡す領収書の取引内容は、明細を列挙せず `ご飲食代として` の1行に固定する。商品、自由入力明細、サービス料などの確定明細は会計記録として保存・再現できるようにするが、領収書用 `print_data` に明細配列を返して紙面を組み立て直さない。領収書用RPCはサーバー側で明細を検証・集計し、紙面には取引内容、税率別集計、決済、発行者情報だけを返す。

### 領収書の消費税表示

領収書は会計額とは別に `10%対象 ¥<税込額>（内消費税 ¥<税額>）` の1行を印字する。課税対象は商品、自由入力明細、サービス料を含む税込会計額の全額とし、税額は `round(total_amount * 10 / 110)` で円単位に丸める。税率・対象額・税額は領収書用RPCがサーバー側で返し、ブラウザで再計算しない。

### 領収書の決済表示

領収書は決済方法ごとに方法名と決済額を別行で印字する。複数決済は `現金 ¥5,000`、`クレジット ¥5,000` のように列挙し、`CAT` は紙面では `クレジット` と表示する。0円会計は決済行を作らず `請求なし 0円` と表示する。領収書用RPCが決済行を返し、ブラウザで方法名の連結や金額の再配分をしない。

現金の預り金と釣銭は会計処理の確認情報であり、領収書の紙面と領収書用 `print_data` には含めない。

### 過去会計の領収書再試行

営業日締め後を含む確定済み伝票の検索・再試行一覧は将来候補として残すが、今回の後続実装範囲には入れない。入口画面、実装時期、検索RPCの契約は未決定である。実装する場合は営業日、会計確定日時、卓番、会計額を表示し、取消済み伝票を表示・再試行対象から除外する。`checkout_id` と `slip_no` は内部管理に留め、一覧の表示キーや紙面に使わない。

### 適格簡易請求書

領収書は、飲食店で交付できる適格簡易請求書の必要事項を、確定済み会計と会計確定時の発行者スナップショットから再現できるようにする。保存対象は発行者名・登録番号、取引日、取引内容、税率ごとの対価額、税率ごとの消費税額または適用税率である。商品、自由入力明細、サービス料を含む課税対象は当面すべて消費税10%固定とし、領収書の税込会計額を10%対象額として扱う。宛名、物理印刷の成否、再発行回数、紙面画像は保存対象にしない。必要事項を確認できる会計・決済・明細データが領収書の写しに相当し、同じデータから再発行できる。発行者情報は、法人名・適格請求書登録番号を `company_master`、店舗表示名・住所・電話番号・ロゴを `department_master` に持たせて扱う。軽減税率、非課税、複数税率を扱う場合は別仕様として税区分と税率別集計を追加する。

本番移行前に、適格簡易請求書としての保存項目、紙面表示、税率別集計、運用を税理士へ確認する。確認前の仕様はテスト運用の前提であり、税務上の最終判断に代えない。

領収書の担当者個人印欄は、80mm紙の末尾に「担当者印」と表示した20mm四方の空欄枠で印字し、会計を担当した店舗スタッフが自身の印を物理的に押印する。印影画像や担当者IDを設定値、印字データ、会計データに持たせない。

### 発行者情報とデータ移行

領収書の会社名、住所、電話番号、店舗ロゴ、適格事業者番号などの発行者情報は、マスタ編集画面の有無にかかわらず `company_master` / `department_master` に持たせる。画面実装前のサンプル値も同マスタへseedする。`ReceiptPrinter` はプリンター接続設定だけを持ち、発行者情報は持たない。担当者個人印はマスタ・設定のどちらにも含めない。

店舗ロゴの初期サンプル値は `【テストロゴ】` の文字印字とし、画像ロゴの印字やSII Web SDK Serverの画像連携は別タスクとする。

スキーマやRPC契約を変更しても、既存行への互換処理、値補完、旧契約の併存は既定要件にしない。既存データを引き継ぐ必要が生じた変更だけ、対象行と移行方法を別途決める。

### 発行者スナップショット

会計確定と同じトランザクションで、発行者情報を `store_checkouts.issuer_snapshot jsonb` へ値コピーして固定する。`issuer_snapshot` は `schema_version = 'issuer-v1'`、法人名、適格請求書登録番号、店舗表示名、住所、電話番号、ロゴを持ち、担当者個人印は含めない。値の元は法人名・登録番号を `company_master`、店舗表示名・住所・電話番号・ロゴを `department_master` とする。これらの項目が欠けていても会計確定は止めず、その時点で得られる値を保存する。`store.get_checkout_receipt_print_data` は現在のマスタではなく、この会計確定時スナップショットを返す。既存会計への値補完や旧契約との互換は持たない。

法人名、登録番号、店舗表示名、住所、電話番号が欠けた場合は、保存値を補完せず紙面上だけ `未設定` と明示する。ロゴは適格簡易請求書の必須事項ではないため、未設定表示の対象にせず、空欄または初期サンプルロゴのまま扱う。

### カラオケ数量の保存

営業中トップのカラオケ数量は、短周期の自動保存に依存しない。アプリ内遷移時に未保存変更を保存し、保存成功を確認してから遷移する。営業中トップでタブ再読み込みが必要な運用は想定せず、再読み込みは防止対象とする。

### 自由明細入力

自由明細は客追加などと同様に専用モーダルで入力し、明示的な保存操作でDBへ反映する。会計時に自由明細の未保存入力を別途チェックする前提にはしない。

自由明細モーダルで入力途中にキャンセルや閉じる操作をした場合、未保存内容は破棄する。ただし入力済みなら「保存せず閉じますか？」を確認し、未保存事故をモーダル内で扱う。

### 注文保存時の伝票有効性確認

注文端末は未保存キューを他端末へ共有しない。注文保存時に対象伝票が会計済み、削除済み、営業日違いなどで無効になっていないかを再確認し、無効な伝票への保存を止める責務を持つ。
